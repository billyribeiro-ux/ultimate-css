CSS vs JavaScript for Animation Performance

"Which is faster, CSS or JavaScript?" is the wrong question. In the nuanced spirit of Josh Comeau's animation writing, this lesson reframes it: both ultimately feed the same compositor, so the real decision is about who drives the values, which thread does the work, and how much control you need. Here is when each approach wins — and the trade-offs that decide it.

The myth: "CSS animations are faster"

It is repeated everywhere, but it is only half true. A CSS transition on transform and a JavaScript loop that sets transform can both run on the GPU compositor at 60fps. The performance of an animation is determined mostly by which property you animate (Lesson 20.2) — not by the language that sets it.

The meaningful difference is where the per-frame work happens:

  • CSS transitions & @keyframes can be handed off entirely to the compositor thread. Once started, they keep running smoothly even if the main thread is busy executing JavaScript.
  • JavaScript animations (via requestAnimationFrame) compute each frame's value on the main thread. If that thread is blocked — a big render, a heavy event handler — the animation stutters, even when it only touches compositor-friendly properties.

So the headline trade-off: CSS can be main-thread-independent; raw rAF JavaScript cannot.

When CSS wins

Reach for CSS first. It is declarative, the browser optimizes it, and it survives main-thread jank.

  • State transitions. Hover, focus, :checked, a toggled class, @starting-style enter/exit — anything that animates between two known states.
  • Looping ambient motion. Spinners, pulses, marquees, gradient drifts — @keyframes with animation-iteration-count: infinite.
  • Scroll-driven effects where supported — animation-timeline: scroll() / view() run off the main thread entirely (Module 9), something JS scroll handlers can never match.
/* Declarative, interruptible, compositor-offloaded */
.card {
  transition: transform 0.25s ease, opacity 0.25s ease;
}
.card:hover { transform: translateY(-4px) scale(1.02); }

/* Ambient loop — zero JS, never blocks */
@keyframes pulse { 50% { opacity: 0.5; } }
.dot { animation: pulse 1.5s ease-in-out infinite; }

When JavaScript wins

CSS can only interpolate between values you declare ahead of time. The moment the animation depends on runtime information, JavaScript earns its place.

  • Dynamic targets. Animate to a position you only learn at runtime — a dragged element's release point, a tooltip anchored to the cursor, a value typed by the user.
  • Physics & springs. Spring motion has no fixed duration; it settles based on velocity and stiffness. This is intrinsically imperative — the realm of libraries like Framer Motion / Motion One, or hand-rolled springs.
  • Gesture-driven & interruptible-mid-flight. Swipe-to-dismiss, pull-to-refresh, scrubbing — the user's finger is the timeline, and the animation must track and hand off to inertia.
  • Complex orchestration. Staggered sequences with branching, conditional steps, or coordination across many elements with precise timing.
  • FLIP layout animations. Animating a layout change (reorder, expand) by measuring before/after and animating the delta with transforms — measurement requires JS.
// FLIP: measure layout, then animate the delta on the GPU.
const first = el.getBoundingClientRect();
reorderTheDOM();                       // layout changes
const last = el.getBoundingClientRect();
const dx = first.left - last.left;
const dy = first.top  - last.top;

el.animate(
  [{ transform: `translate(${dx}px, ${dy}px)` }, { transform: 'none' }],
  { duration: 300, easing: 'ease' }    // WAAPI → compositor
);

The bridge: the Web Animations API (WAAPI)

It is not a binary choice. element.animate() gives you JavaScript's control and CSS's compositor offloading: animations created with WAAPI on transform/opacity can run off the main thread just like CSS, while remaining fully scriptable, pausable, reversible, and composable.

const anim = el.animate(
  [{ transform: 'translateX(0)' }, { transform: 'translateX(300px)' }],
  { duration: 400, easing: 'cubic-bezier(.2,.8,.2,1)', fill: 'both' }
);

anim.pause();           // imperative control...
anim.playbackRate = 2;  // ...with compositor performance
anim.reverse();

Rule of thumb: if you need JS control but the animation is just transform/opacity, prefer WAAPI over a requestAnimationFrame loop — you keep the main thread free.

The interruption test (a Josh-Comeau favorite)

A great way to choose: what happens if the user interacts mid-animation? CSS transitions interrupt gracefully — change the target state and the browser re-interpolates from the current position. CSS @keyframes do not; they snap or restart. JS/WAAPI give you full control to redirect from the live value. If your animation must be reversible or redirectable at any instant, that pushes you toward WAAPI or a JS library.

The cost JavaScript carries

Choosing JS is not free, and the trade-offs are real:

  • Bundle weight. A physics library is JS the user must download, parse, and execute — competing with your CSS-free baseline of zero bytes.
  • Main-thread contention. A requestAnimationFrame loop doing layout reads/writes can trigger forced synchronous reflows ("layout thrashing"). Batch reads, then writes.
  • Reduced-motion duty. CSS honors prefers-reduced-motion with a media query you already know. In JS you must check it explicitly with matchMedia and provide the reduced path yourself.
// Accessibility is your job in JS:
const reduce = matchMedia('(prefers-reduced-motion: reduce)').matches;
el.animate(keyframes, { duration: reduce ? 0 : 400 });

The decision framework

Walk down this list and stop at the first match:

  1. Two known states, triggered by interaction or class change? → CSS transition.
  2. Looping/ambient or scroll-linked motion? → CSS @keyframes / scroll-driven animations.
  3. Need scripted control (pause, reverse, dynamic target) but only animating transform/opacity? → WAAPI.
  4. Spring physics, gestures, FLIP, or complex orchestration? → JavaScript (library or hand-rolled), driving transform/opacity.

The through-line: whatever drives the values, animate compositor-friendly properties. The CSS-vs-JS question is about control and the main thread; the fast-vs-janky question is still about transform and opacity.

Try it yourself

Mini-exercise

Build a swipe-to-dismiss card and justify your tooling. (1) Use a CSS transition for the resting hover lift. (2) Use a pointer-driven JS handler for the drag, setting transform: translateX() live from the finger position. (3) On release, hand off to a WAAPI animation that either snaps back or flings off-screen based on velocity. (4) Gate all motion behind a matchMedia('(prefers-reduced-motion: reduce)') check. Explain, in a comment, why each phase uses the driver it does — that justification is the real deliverable.
