Lesson 16.3 · Real-World Layout

The Long-Form Article (Medium/Substack Style)

A beautiful reading experience: centered prose at 65ch, drop caps, pull quotes, a sticky progress bar, and a table of contents sidebar that collapses on narrow viewports. Every detail serves readability.

The typographic system

Long-form articles live and die by their typography. The optimal line length is 55-75 characters (65ch is the sweet spot). The font size is 1.125rem minimum on desktop, with line-height at 1.7-1.8 for comfortable scanning. Paragraph spacing uses margin-block-start instead of margin-block-end so the first paragraph naturally has no gap above it.

The drop cap

The first paragraph's ::first-letter is styled with a large font size (3.5em), floated inline-start, and given a small margin. The key trick: line-height: 0.8 prevents the drop cap from pushing down the second line excessively.

The reading progress bar

A fixed-position element at the top of the viewport uses animation-timeline: scroll() to grow its inline-size from 0% to 100% as the user scrolls the article. No JavaScript needed — the scroll position directly drives the progress.

The table of contents sidebar

On wide viewports (above 72rem), the layout becomes a two-column grid with the TOC in a sticky sidebar. On narrow viewports, the TOC collapses into a disclosure widget (<details>) above the article. This is the classic responsive sidebar pattern.

On the Virtue of Removing Code

Sarah Chen
12 min read · March 2026

Every line of code is a liability. This is not a new observation, but it is one that most teams forget the moment they open a pull request. The urge to add is strong. The discipline to subtract is rare. And yet the most impactful engineering work I have witnessed in twenty years has been deletion.

The case for simplicity

Simplicity is not the absence of features. It is the presence of clarity. When a system is simple, every part serves a purpose that a new team member can understand in minutes, not days. The code reads like prose because it was edited like prose — draft after draft, removing words until only the necessary ones remain.

Consider the Array.prototype.reduce method. In a single function call, it replaces loops, accumulators, and intermediate variables. It is simple not because it is short, but because it communicates intent without ceremony.

The best code is the code that was never written. The second best is the code you had the courage to delete.

Complexity as debt

Every abstraction has a carrying cost. Every layer of indirection is a tax on the next developer who must trace a bug through the stack. We call this "technical debt" but the metaphor is imprecise. Debt implies a conscious borrowing with intent to repay. Most complexity accumulates not through deliberate trade-offs but through inattention — the slow accretion of "just one more" until the system collapses under its own weight.

The rewrite trap

The temptation, when facing a complex system, is to rewrite it from scratch. This is almost always wrong. A rewrite discards hard-won knowledge embedded in edge-case handling, error recovery, and performance optimizations that were added one painful bug at a time over years.

The problem with rewrites is not that they fail to deliver the new architecture. It is that they fail to deliver the old behavior.

Instead of rewriting, reduce. Find the seams. Extract the unnecessary. Inline the over-abstracted. Delete the dead code that everyone is afraid to touch because "it might be used somewhere."

Principles of reduction

First, measure. You cannot simplify what you do not understand. Map the dependencies. Count the call sites. Profile the hot paths. Only then can you know which removals will have the greatest impact with the least risk.

Second, automate the verification. Every deletion should be backed by a test that proves the system still behaves correctly. If you cannot write that test, you do not understand the code well enough to delete it safely.

Third, communicate the intent. A deletion pull request with no description terrifies reviewers. Explain what was removed, why it existed in the first place, and what evidence shows it is no longer needed. The commit message is a letter to your future self.

Key takeaway

A beautiful reading experience requires no framework, no build tool, no JavaScript. The optimal max-inline-size: 65ch, proper line-height, and ::first-letter styling create a Medium-quality reading experience. The scroll-driven progress bar is a single element with animation-timeline: scroll(). Typography is the highest-leverage CSS skill.
