Lesson 4.8

Semantic Token Aliasing at Scale

Two tiers are enough for most projects. Three tiers are the right answer the moment the product has per-component theming, user-selectable themes, or tightly customised surfaces. The third tier is component tokens, and they inherit their defaults from semantic tokens.

The three-tier model

  1. Primitive tokens — raw values. --purple-500, --gray-100, --space-4. Stable, rarely touched.
  2. Semantic tokens — product intentions. --color-brand, --color-surface, --space-gutter. Repointed during rebrands.
  3. Component tokens — per-component surfaces. --btn-bg, --card-padding, --dialog-radius. Scoped to the component; default from semantic tokens; overridable by variants and consumers.

The chain runs top to bottom:

--purple-500: oklch(55% 0.22 290);    /* primitive */
--color-brand: var(--purple-500);      /* semantic  */
.btn { --btn-bg: var(--color-brand); } /* component */

Each tier has one job. Primitives are data. Semantics are meaning. Component tokens are the public API of the component.

Theme switching with data attributes

A theme is a remapping of semantic tokens. Primitives stay stable; semantics point at different primitives per theme. The canonical pattern uses a data-theme attribute on the root:

:root {
  --gray-50:  oklch(98% 0.003 264);
  --gray-900: oklch(14% 0.015 264);
  --purple-400: oklch(68% 0.18 290);
  --purple-500: oklch(55% 0.22 290);
}

:root[data-theme="light"] {
  --color-surface: var(--gray-50);
  --color-text:    var(--gray-900);
  --color-brand:   var(--purple-500);
}

:root[data-theme="dark"] {
  --color-surface: var(--gray-900);
  --color-text:    var(--gray-50);
  --color-brand:   var(--purple-400);
}

Flipping document.documentElement.dataset.theme = "dark" switches every component that reads semantic tokens, in one line of JavaScript, with no re-render.

Component tokens give consumers a knob

A button component exposes --btn-bg as its public interface. By default it comes from a semantic token. Consumers can override it per instance without writing a new class:

.btn {
  --btn-bg: var(--color-brand);
  --btn-fg: #fff;
  background: var(--btn-bg);
  color: var(--btn-fg);
}

/* Variant — one property changes */
.btn.danger { --btn-bg: var(--color-danger); }

/* Ad-hoc override via inline style or parent scope */
.marketing-hero .btn { --btn-bg: var(--color-accent); }

The component's internals never change. The consumer never rewrites a rule. The customisation surface is the set of component tokens the component chose to expose, and exposing that surface is a deliberate API decision.

The rules for the three tiers

  • Components only consume component tokens and semantic tokens — never primitives.
  • Semantic tokens only reference primitives, never component tokens.
  • Theme switches only remap semantic tokens. They do not touch primitives or components.
  • A component's exposed token surface is part of its public contract. Renaming --btn-bg is a breaking change, same as renaming a function.

When two tiers are enough

Small products, single theme, no per-instance customisation — skip component tokens. The consumer writes .btn { background: var(--color-brand); } and ships. The moment you need a second theme, per-feature overrides, or a design system used by multiple apps, add the third tier. Adding it later is straightforward; skipping it when you need it is painful.
