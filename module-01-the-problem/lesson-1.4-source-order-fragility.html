Lesson 1.4

Source Order Fragility

Source order as a cascade tiebreaker sounds simple. In practice, it is a trap that detonates the moment you split CSS across files, use a build tool, or import third-party stylesheets.

The rule everyone knows

When two rules have identical specificity, the one that appears later wins. This sounds predictable. It stops being predictable the moment you have more than one file.

The trap

A design system file imports before a component file. Both target .btn with identical specificity. The component wins because it is last. Six months later, the build configuration changes and imports are reordered. The design system now wins. Nothing in the code changed — only the import order. The bug is silent and invisible until a designer notices a button looks wrong.

What affects source order

  • @import ordering inside CSS files.
  • <link> tag ordering in HTML.
  • Bundler behavior — which file gets concatenated first?
  • Deferred scripts that inject styles after parse.

Why this is a smell, not a bug

A codebase where swapping the order of two imports changes the output is a codebase whose CSS architecture does not exist. @layer makes order explicit: you declare layer priority once, and physical file order no longer matters.

Mini-exercise

Create two conflicting rules at identical specificity in the editor above. Swap their order repeatedly. Note that nothing about the selectors or the values has changed — only the position. Internalize how fragile this tiebreaker is when you can't see both files at once.
