Lesson 1.3

The Specificity War: How Projects Collapse

A narrative lesson. No new syntax. We trace a codebase from day one to day 365 and watch it become unmaintainable — not because the developers were bad, but because the system has no way to express architectural intent.

Month 1 — clean

Three files, clean selectors, everything works. .btn targets buttons. .card targets cards. Life is good.

Month 3 — the third party arrives

A UI library is added to accelerate development. Its selectors are more specific than yours. Your .btn (0,1,0) stops applying because .ui-toolkit .btn (0,2,0) wins.

Month 5 — the doubled class

A developer fixes it by writing .btn.btn (0,2,0) — now tying with the library. Source order saves it. For now.

Month 7 — the first !important

A new feature needs a variant that overrides the doubled class. The only known fix is !important. It ships.

Month 9 — the death spiral

Three developers have independently added !important to fight each other's !important. A new developer joins and has no idea what is safe to change.

Month 12 — debt

The stylesheet is 4,000 lines. Everyone is afraid to modify it. Specificity debt is real.

The lesson

This is not caused by incompetent developers. It is caused by a system that has no first-class way to express "this style is a reset, this style is a base, this style is a component." @layer adds that missing dimension.
