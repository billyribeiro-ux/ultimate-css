Lesson 8.7

Form Fields with :has() Validation

Every form validation library you have ever used exists to answer one question: "is this input valid right now?" — and then toggle a class on its wrapper. :has() plus native HTML constraint validation answers it in CSS.

The three-selector trick

.field                                                  { --field-accent: var(--color-border-strong); }
.field:has(input:focus)                                 { --field-accent: var(--color-primary); }
.field:has(input:invalid:not(:placeholder-shown))       { --field-accent: var(--color-danger); }
.field:has(input:valid:not(:placeholder-shown))         { --field-accent: var(--color-success); }

Four rules, four states. The field wrapper derives its border and label color from --field-accent. The individual rules only touch the custom property — never the actual border-color — so overriding is still a one-line change.

Why :not(:placeholder-shown)

Without that qualifier, an empty required field is "invalid" the instant the page loads. The user sees red before typing anything, and learns to ignore validation. :placeholder-shown means "the field is empty and showing its placeholder" — so :not(:placeholder-shown) means "the user has actually entered something". That makes validation appear only after interaction, which is what users expect.

Native constraints you can style

  • required → participates in :invalid when empty.
  • type="email", type="url" → format validation for free.
  • pattern="..." → regex validation without JavaScript.
  • minlength, maxlength, min, max, step.

Accessibility

:invalid is purely visual. For screen readers, add aria-invalid via the platform's own form events, or use aria-describedby pointing at an error message element. CSS handles the paint; ARIA handles the announcement. The two layers are complementary, not competitive.

Browser support

:has() is baseline. Native constraint validation is baseline. This lesson teaches a production-ready pattern — no @supports needed.
