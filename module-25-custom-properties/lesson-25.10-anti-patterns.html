Lesson 25.10 · Custom Properties

Custom Property Anti-Patterns

Custom properties are powerful, but misuse creates maintenance nightmares. Here are the six most common mistakes — with before/after examples showing the fix for each one.

1. Too many properties on :root

Declaring 30+ custom properties on :root creates an unreadable wall of tokens with no organization or scoping.

Before (bad)

:root {
  --color-primary: oklch(55% 0.22 275);
  --color-primary-light: oklch(70% 0.15 275);
  --color-primary-dark: oklch(40% 0.18 275);
  --color-secondary: oklch(55% 0.15 150);
  --color-secondary-light: oklch(70% 0.1 150);
  /* ...25 more lines... */
  --spacing-xs: 0.25rem;
  --spacing-sm: 0.5rem;
  /* ...and so on... */
}

After (fixed)

/* Group by system, derive from base values */
:root {
  --hue-primary: 275;
  --hue-secondary: 150;
  --space-unit: 0.25rem;
}
/* Component-level derivation */
.btn {
  --btn-bg: oklch(55% 0.22 var(--hue-primary));
  --btn-spacing: calc(var(--space-unit) * 3);
}

Keep :root to base inputs (hues, units, multipliers). Derive everything else at the component level.

2. Using custom properties for everything

Not every value needs to be a token. Static values that never change and are used once gain nothing from abstraction.

Before (bad)

.tooltip {
  --tooltip-z: 1000;
  --tooltip-arrow-size: 6px;
  --tooltip-max-width: 200px;
  z-index: var(--tooltip-z);
  max-width: var(--tooltip-max-width);
}

After (fixed)

.tooltip {
  z-index: 1000;          /* never changes */
  max-width: 200px;       /* never overridden */
  --tooltip-bg: oklch(20% 0.02 0); /* this one IS themeable */
  background: var(--tooltip-bg);
}

Only create a custom property if the value is: themed, responsive, shared between elements, or overridden by variants.

3. Deep fallback chains

Three or more nested var() calls make debugging which value is active nearly impossible.

Before (bad)

background: var(--card-bg,
  var(--section-bg,
    var(--page-bg,
      var(--surface,
        oklch(98% 0.01 275)))));

After (fixed)

/* Resolve at definition, not at usage */
.card {
  --_bg: var(--card-bg, var(--surface, oklch(98% 0.01 275)));
  background: var(--_bg);
}

Limit to 2 levels. Use a private property (--_ prefix) to pre-resolve the chain.

4. Relying on IACVT behavior intentionally

Some developers use "invalid at computed-value time" as a feature — setting a property to a wrong type to trigger the initial value. This is fragile and confusing.

Before (bad)

/* "Trick" to reset to initial by setting wrong type */
.hidden { --display: not-a-display-value; }
.box { display: var(--display, flex); }
/* When .hidden: IACVT → display inherits → unpredictable */

After (fixed)

/* Explicit state with clear values */
.box { --show: 1; }
.box.hidden { --show: 0; }
.box { display: flex; opacity: var(--show); }

Never rely on IACVT for logic. Use explicit values and the space toggle if you need binary state.

5. Setting properties in keyframe animations

Animating custom properties inside @keyframes without @property registration causes style recalculation on every frame for all consumers.

Before (bad)

@keyframes pulse {
  0%   { --scale: 1; }
  50%  { --scale: 1.2; }
  100% { --scale: 1; }
}
/* Browser can't interpolate — snaps between values */

After (fixed)

@property --scale {
  syntax: "<number>";
  inherits: false;
  initial-value: 1;
}
@keyframes pulse {
  50% { --scale: 1.2; }
}
/* Now the browser interpolates smoothly */

6. Forgetting @property for animated properties

Without registration, the browser treats custom properties as strings. Transitions and animations on unregistered properties produce no interpolation — they snap instantly from one value to another.

Before (bad)

.progress {
  --value: 0;
  width: calc(var(--value) * 100%);
  transition: width 0.3s;
  /* Transition works on width, but if you transition --value
     directly, it snaps without @property */
}

After (fixed)

@property --value {
  syntax: "<number>";
  inherits: false;
  initial-value: 0;
}
.progress {
  --value: 0;
  width: calc(var(--value) * 100%);
  transition: --value 0.3s;
}
.progress.full { --value: 1; }
/* Smooth interpolation of the custom property itself */

Summary reference

  • 1
    Too many :root properties Keep :root to base inputs. Derive at component level.
  • 2
    Abstracting static values Only tokenize values that are themed, shared, or overridden.
  • 3
    Deep fallback chains (3+ levels) Limit to 2 levels. Pre-resolve with a private property.
  • 4
    Intentional IACVT abuse Use explicit values or the space toggle for binary state.
  • 5
    Animating without @property Register properties for smooth interpolation in keyframes.
  • 6
    Forgetting @property for transitions Unregistered properties snap; registered ones interpolate.

Key takeaway

Custom properties are a tool for communication and reactivity — not a replacement for every hardcoded value. Use them where they add flexibility (theming, state, responsive values) and leave static values as plain CSS. Register animated properties with @property. Keep fallback chains shallow. Your future self (and teammates) will thank you.
