Lesson 25.2 · Custom Properties

Fallback Chains and Default Values

Nested fallbacks let a component gracefully degrade when custom properties are missing. But beware: a property that exists with an incompatible value triggers "invalid at computed-value time" — a subtle trap that every CSS author must understand.

Nested fallbacks

The var() function accepts a fallback as its second argument. That fallback can itself be another var():

color: var(--brand-color, var(--accent, var(--fallback, oklch(55% 0.2 275))));

The browser resolves left to right: if --brand-color is defined, use it. Otherwise try --accent. Then --fallback. Finally the literal value.

The guaranteed-defined pattern

Always provide a concrete fallback at the usage site so the component works even when no property is set:

.card {
  background: var(--card-bg, var(--surface, oklch(98% 0.01 275)));
  color: var(--card-color, var(--on-surface, oklch(20% 0 0)));
}

Invalid at computed-value time (IACVT)

When a custom property is defined but holds a value incompatible with the property it is used in, the browser does not use the fallback. Instead, the property becomes "invalid at computed-value time" and the property resets to its inherited value (or initial if not inherited):

:root { --size: blue; }
.box  { width: var(--size, 100px); }
/* --size exists, so fallback is skipped.
   "blue" is invalid for width.
   Result: width inherits or goes to initial (auto). */

Missing vs. invalid

Key distinction:

  • Missing property (never declared) — fallback kicks in.
  • Invalid value (property exists, value wrong) — IACVT, no fallback, inherits initial.

This is why @property registration matters: it lets the browser validate the type at parse time rather than failing silently at computed-value time.

The @property safety net

Register your custom properties with @property to avoid IACVT surprises. Registered properties validate the value at parse time:

@property --card-bg {
  syntax: "<color>";
  inherits: true;
  initial-value: oklch(98% 0.01 275);
}
/* Now "not-a-color" is rejected at parse time,
   and the initial-value kicks in instead of IACVT */

Fallback strategies by use case

Component tokens: Use a component-level fallback referencing a system token:

.card { background: var(--card-bg, var(--surface)); }

System tokens: Provide a literal at the end of the chain:

:root { --surface: var(--theme-surface, oklch(98% 0.01 275)); }

Derived values: Use private properties to pre-resolve complex chains:

.card {
  --_bg: var(--card-bg, var(--surface, oklch(98% 0.01 275)));
  background: var(--_bg);
}

Best practices

Keep fallback chains to 2 levels maximum. Beyond that, debugging which value is active becomes impractical. Use private properties (prefixed with --_) for intermediate resolution. Always end a chain with a concrete literal value. Document the fallback priority in comments for future maintainers.

Testing fallbacks in DevTools

Chrome and Firefox DevTools show which custom property value is active. To test fallback behavior:

  1. Inspect the element and find the computed value of the property.
  2. In the Styles panel, uncheck (disable) the custom property definition.
  3. Watch the computed value shift to the next fallback level.
  4. Repeat to walk through the entire chain.

This workflow reveals the resolution order visually, making fallback chains debuggable even when the CSS is complex.

Common fallback architectures

Design systems typically use a two-tier model: a global token layer (--color-primary) and a component token layer (--btn-bg). The component token falls back to the global token, which falls back to a literal. This gives you exactly 2 levels — the sweet spot for flexibility without confusion:

/* Global (system tokens) */
:root { --color-primary: oklch(55% 0.22 275); }

/* Component (references system) */
.btn { background: var(--btn-bg, var(--color-primary)); }

Try it yourself

Quick reference: fallback resolution

  • var(--a) — no fallback. If missing: IACVT.
  • var(--a, red) — fallback to literal if --a is missing.
  • var(--a, var(--b, red)) — chain: try a, then b, then literal.
  • A property set to initial is "guaranteed invalid" — treated as missing.
  • A property set to any other value is "defined" — even if incompatible with usage site.

Mini-exercise

Add a fourth box with --box-bg: not-a-color. Observe what happens: the background will not be the fallback (because --box-bg exists), but it will not be "not-a-color" either. The browser triggers IACVT and the background resolves to the inherited or initial value. This is the trap to remember.
