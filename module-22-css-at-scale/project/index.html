Architecture Decision Record

An ADR documents why a technical decision was made. This template captures the PE7 architecture decision as an example. Use this format for any CSS architecture proposal your team evaluates.

ADR-001: Adopt PE7 CSS Architecture

Status
Accepted
Date
2026-01-15
Decision Makers
Frontend Architecture Team
Supersedes
ADR-000 (BEM + SCSS Architecture)

Context

Our current CSS architecture uses BEM naming with SCSS compilation. We have 12,000 lines of CSS across 3 applications. Pain points include:

  • Specificity conflicts requiring !important (47 instances across the codebase)
  • Inconsistent naming conventions between teams (some use BEM, some use utility classes)
  • No architectural boundary enforcement — any file can override any other file
  • Theme support requires duplicating component styles per theme
  • Design tokens are hard-coded values scattered across component files

Decision

We will adopt the PE7 architecture: @layer for cascade control, @scope for component boundaries, and custom properties for theming and component APIs. Migration will follow the incremental strategy (Lesson 22.6) over 6 months.

Key architectural choices:

  • Layer order: reset, tokens, base, layouts, components, utilities, overrides
  • All design tokens centralized in the tokens layer as custom properties
  • Component APIs exposed via documented custom properties
  • Themes implemented as token reassignment via data attributes
  • No naming convention enforced — @scope provides encapsulation

Consequences

Positive: Zero specificity conflicts (layers control order). Theme support without component duplication. Clear ownership model for tokens. Architecture is enforced by the browser, not by developer discipline.

Negative: Requires modern browser baseline (no IE11). Team needs training on @layer and @scope. Existing SCSS tooling must be deprecated. 6-month migration period with legacy and modern code coexisting.

Risks: Incomplete migration leaving the codebase in a hybrid state. Team resistance to abandoning familiar BEM patterns. Third-party CSS libraries that do not use @layer requiring wrapper layers.

Architecture Evaluation Checklist

  • Does it prevent specificity conflicts at scale?
  • Does it support multiple themes without component duplication?
  • Does it centralize design tokens with clear ownership?
  • Does it provide component encapsulation?
  • Can it be adopted incrementally?
  • Does it work with third-party CSS?
  • Does it reduce or eliminate !important usage?
  • Can architecture violations be detected automatically?
  • Does it have a clear documentation pattern?
  • Does it support the required browser matrix? (verify per project)

ADR Template

Use this structure for any CSS architecture decision your team faces:

ADR-[number]: [Title]

Status: [Proposed | Accepted | Deprecated | Superseded]
Date: [YYYY-MM-DD]
Decision Makers: [Team or individuals]
Supersedes: [Previous ADR if applicable]

## Context
What problem are we solving? What pain points exist?
What constraints do we operate under?

## Decision
What architecture did we choose? Why?
What are the key structural choices?

## Consequences
Positive: What improvements do we expect?
Negative: What trade-offs are we accepting?
Risks: What could go wrong?

## Review Date
When will we revisit this decision?

When to write an ADR

Write an ADR when: adopting a new methodology, introducing a build tool, changing the token structure, adding a new layer, or deprecating a pattern. Do not write an ADR for individual component decisions or single-property styling choices. The threshold: if the decision affects multiple developers or multiple sprints of work, it deserves an ADR.

Your task

Write your own ADR for a CSS architecture decision. It can be PE7, BEM, CUBE, or a hybrid approach. Use the Context, Decision, Consequences format. Fill in the evaluation checklist honestly — no architecture scores perfectly on every criterion. The value of the ADR is not the decision itself, but the documented reasoning that future developers can reference when they ask "why did we do it this way?"
