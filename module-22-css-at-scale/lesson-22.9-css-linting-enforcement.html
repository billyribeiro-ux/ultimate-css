CSS Linting & Automated Enforcement

The 7 Non-Negotiable Rules from Lesson 3.9 are only as strong as the enforcement behind them. Manual review catches violations after they are written. Automated linting catches them as they are typed.

Stylelint: the standard CSS linter

Stylelint is the dominant CSS linter. It parses real CSS (not regex matching), understands modern syntax including @layer, @scope, and nesting, and supports a pluggable rule system. It runs in the terminal, in CI, and in editors. It is to CSS what ESLint is to JavaScript: the single tool every team should configure before writing a line of production CSS.

Stylelint works by parsing your CSS into an abstract syntax tree and running rules against every node. Built-in rules cover syntax, convention, and known anti-patterns. Community plugins extend coverage to architecture enforcement, performance, and accessibility. Custom rules let you encode team-specific constraints that no generic tool could anticipate.

The critical property of Stylelint is that it is configurable. An unconfigured linter is noise. A well-configured linter is governance. The difference between the two is a single configuration file that encodes your architecture as machine-readable rules.

A PE7 Stylelint configuration

The following .stylelintrc.json encodes the 7 Non-Negotiable Rules as lint checks. Each rule maps to a specific architectural constraint from Lesson 3.9. When this configuration runs, violations are caught at authoring time rather than review time.

{
  "rules": {
    "declaration-no-important": true,

    "color-named": "never",
    "color-no-hex": true,

    "selector-max-specificity": "0,3,0",
    "selector-max-id": 0,

    "property-disallowed-list": [
      "margin-left",
      "margin-right",
      "padding-left",
      "padding-right",
      "top",
      "bottom",
      "left",
      "right"
    ],

    "custom-property-pattern": "^(color|space|radius|shadow|font|text|line|border|z)-",

    "at-rule-disallowed-list": []
  }
}

Rule by rule:

Rule 1 — No !important: declaration-no-important forbids !important everywhere. In the PE7 architecture, layer order eliminates every legitimate use of !important outside the animations layer. If you need an override, move the declaration to a higher layer rather than forcing specificity.

Rule 2 — No hard-coded colors: color-no-hex and color-named: never together forbid hex values and named colors like red or rebeccapurple. All color values must come from custom properties defined in the tokens layer. This guarantees theme consistency and makes dark mode support a token swap rather than a component rewrite.

Rule 3 — No physical direction properties: property-disallowed-list bans margin-left, margin-right, padding-left, padding-right, top, bottom, left, and right. Use the logical equivalents: margin-inline-start, margin-inline-end, padding-inline-start, padding-inline-end, inset-block-start, inset-block-end, inset-inline-start, inset-inline-end. This is not optional for internationalization — it is a prerequisite.

Rule 4 — No class selectors in the base layer: This rule is best enforced by file-level convention: base-layer files should contain only element selectors. Stylelint can enforce this with a per-file override using the overrides key, restricting selector-max-class to 0 in files matching a base/** glob pattern.

Rule 5 — Max selector specificity: selector-max-specificity: "0,3,0" caps specificity at three classes, zero IDs. selector-max-id: 0 makes the ID ban explicit. In a layered architecture, specificity is a secondary concern — layer order is primary — but capping it prevents the arms race that layers were designed to end.

Rule 6 — Require logical properties: Covered by the property-disallowed-list above. The disallowed list acts as a forcing function: developers who type margin-left see an immediate error and learn the logical equivalent.

Rule 7 — Require @layer wrapping: Enforcing that all rules live inside a @layer block is the hardest rule to automate with built-in Stylelint. The at-rule-disallowed-list entry is a placeholder — in practice, this is best enforced with a custom plugin or a grep-based CI check that fails if any CSS file contains top-level rules outside a @layer block.

CI integration

A lint check that runs only on developer machines is a suggestion. A lint check that runs in CI is a gate. The following GitHub Actions workflow runs Stylelint on every pull request:

name: CSS Lint
on: [pull_request]
jobs:
  stylelint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - name: Lint CSS
        run: npx stylelint "**/*.css" --config .stylelintrc.json

This runs in seconds. A failing lint check blocks the PR from merging. No negotiation, no exceptions. The configuration file is the single source of truth for what constitutes valid CSS in your project.

Pair this with the visual regression tests from Lesson 22.8 for a two-layer CI pipeline: lint catches mechanical violations in seconds, visual regression catches rendering issues in minutes. Fail fast on the cheap check.

Editor integration

CI catches violations before merge. Editor integration catches violations before commit. Add the Stylelint extension to VS Code and configure it to validate on save:

{
  "stylelint.validate": ["css"],
  "css.validate": false,
  "editor.codeActionsOnSave": {
    "source.fixAll.stylelint": "explicit"
  }
}

With this configuration, violations appear as red underlines as the developer types. Auto-fixable rules (like replacing margin-left with margin-inline-start) are corrected on save. The feedback loop shrinks from hours (code review) to seconds (editor underline).

Every developer on the team must use the same Stylelint configuration. Commit the .stylelintrc.json to the repository root. Commit the VS Code settings to .vscode/settings.json. Configuration that is not in version control is configuration that drifts.

The enforcement philosophy

Linting is the minimum viable enforcement. It catches the obvious violations: hard-coded colors, !important, physical properties, over-specific selectors. These are mechanical errors with unambiguous fixes.

Code review catches the architectural violations: a component that should use tokens but uses a valid OKLCH value directly, a layout that works but belongs in the wrong layer, a custom property API that is technically correct but poorly designed. These require human judgment.

Together, linting and code review make the PE7 rules self-enforcing. The linter handles the 80% of violations that are mechanical. The reviewer focuses on the 20% that are architectural. Neither is sufficient alone. Both are necessary.

The goal is not to catch every violation — it is to make violations progressively harder to introduce. A developer who sees margin-left underlined in red stops typing it. A developer who sees a CI failure for !important stops reaching for it. Over weeks, the linter trains the team. The rules become habits. The configuration file becomes unnecessary because the team has internalized the architecture.

Demo — Before and after: 5 violations fixed

Before — 5 violations

.alert {
  /* 1: hard-coded hex color */
  background: #ff4444;
  /* 2: physical property */
  padding-left: 1rem;
  /* 3: named color */
  color: white;
  /* 4: !important override */
  display: flex !important;
}
/* 5: ID selector */
#sidebar .alert {
  margin: 2rem;
}

After — all fixed

@layer components {
  .alert {
    /* token from tokens layer */
    background: var(--color-danger);
    /* logical property */
    padding-inline-start: 1rem;
    /* token reference */
    color: var(--color-on-danger);
    /* layer order handles cascade */
    display: flex;
  }
  /* class selector, low specificity */
  .sidebar .alert {
    margin: 2rem;
  }
}
