Lesson 22.6 · Enterprise Architecture

Migrating Legacy CSS to @layer

You cannot rewrite 10,000 lines of CSS in a sprint. The incremental migration strategy wraps existing CSS in a compatibility layer, adds new CSS in proper layers, and refactors one component at a time. Six months, zero regressions.

The incremental approach

The key insight: you do not need to rewrite everything at once. The migration is four steps, each independently deployable.

Step 1: Declare your layer order at the top of your entry point. This single line establishes the architecture.

Step 2: Wrap all existing CSS in a single @layer legacy. This changes nothing visually because specificity relationships within the layer are preserved. The entire existing codebase continues to work identically.

Step 3: Write all new CSS in the appropriate PE7 layer. New features get proper architecture from day one. Old code remains untouched in the legacy layer.

Step 4: Migrate one component at a time from legacy to the correct layer. Each migration is a small, reviewable PR that can be tested independently.

The @import layer() technique

Third-party CSS can be wrapped in a layer at import time: @import url("vendor.css") layer(vendor). This gives you architectural control over CSS you do not own. The vendor layer sits below your layers, so your overrides always win without !important.

This technique works for any external CSS: design system packages, CSS resets, icon libraries, or component frameworks. The layer wrapper is invisible to the library itself — it does not require forking or modifying the source.

/* Wrapping third-party CSS in layers */
@import url("normalize.css") layer(vendor.reset);
@import url("component-lib.css") layer(vendor.components);

/* Your layers always win */
@layer vendor, tokens, base, components, utilities;

Handling !important during migration

Legacy codebases often have !important scattered throughout. During migration, these become problematic because !important reverses layer order — in the important origin, lower layers take priority over higher layers. This means an !important in your legacy layer would beat an !important in your components layer.

The strategy: as you migrate each component, remove its !important declarations. Replace them with proper layer ordering. Track progress: count remaining !important instances weekly. The goal is zero !important usage in the final architecture. During the transition period, some !important may be temporarily necessary — document each one with a comment explaining why and when it can be removed.

The test strategy: visual regression

Before migrating any component, capture screenshots of every state (default, hover, focus, active, disabled, error). After migration, compare screenshots pixel-by-pixel. Any visual difference is a regression that must be resolved before merging. Tools like Playwright's screenshot comparison make this automated and repeatable.

The golden rule: migration must be invisible to users. If a single pixel changes, the migration introduced a bug. Capture screenshots at multiple viewport widths (375px, 768px, 1280px) and in both light and dark themes if applicable.

A realistic 6-month migration plan

Month 1: Declare layers, wrap all existing CSS in @layer legacy, set up visual regression testing infrastructure. Audit the codebase: count components, count !important instances, identify hard-coded values. This month produces zero visual changes but establishes the foundation.

Month 2-3: Extract tokens from hard-coded values, build the token layer. Create the design token file with all colors, spacing, typography, and radii. Update components to reference tokens — this can be done within the legacy layer as an intermediate step.

Month 4-5: Migrate components one at a time (highest-traffic pages first, simplest components first). Each component migration is a single PR: move from legacy layer to components layer, replace BEM classes with @scope where appropriate, remove !important. Target 3-5 components per sprint.

Month 6: Remove the legacy layer (should be empty or nearly empty by now), delete remaining !important usage, run full audit for completeness. Celebrate with the team — the migration is complete.

Demo — Before/after wrapping legacy CSS in layers

Before (legacy)

/* styles.css - 10,000 lines */
.header { ... }
.header .nav { ... }
.header .nav a { ... }
.btn { ... }
.btn!important { color: red; }
.card { ... }
/* specificity wars everywhere */

After (step 1)

/* main.css - entry point */
@layer reset, tokens, base,
       layouts, components, utilities;

/* Wrap everything in legacy */
@import url("legacy.css")
  layer(legacy);

/* New code in proper layers */
@layer components {
  .new-card { ... }
}
Result: Zero visual changes. Legacy CSS is now contained. New CSS goes in proper layers. Migration can proceed component by component with no deadline pressure.

Try it yourself

Mini-exercise

Migrate the legacy .header styles into the proper layers: its colors become tokens, its layout rules move to a layouts layer. Delete the original from @layer legacy. The visual result should be identical — that is the test. Migration preserves appearance while improving architecture.
