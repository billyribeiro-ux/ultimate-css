Designing Component APIs with Custom Properties

A well-designed component exposes a deliberate set of custom properties as its public API. Everything else is private implementation. This contract between component author and consumer enables infinite customization without breaking encapsulation.

The contract: exposed vs hidden

A button component might expose --btn-bg, --btn-color, --btn-radius, and --btn-padding-inline. These are the public API. Internal calculations (how hover state darkens the background, how focus ring width relates to border-radius) remain private. Consumers can customize appearance without understanding implementation.

Default values with var()

The pattern background: var(--btn-bg, oklch(48% 0.18 275)) means the component works out of the box but can be overridden. The fallback is the default. No custom property set? The component looks correct. Custom property set by a parent? The component adapts.

The "open" vs "closed" philosophy

Open components expose many properties (10+), giving consumers maximum flexibility. Risk: breaking changes when internal structure changes. Closed components expose few properties (3-5), offering limited but stable customization. The right choice depends on your team's needs and change tolerance.

When to expose vs when to create a variant

Expose a property when the customization is continuous (any color, any size). Create a variant class when the customization is discrete (small/medium/large, primary/secondary/destructive). Mixing both gives consumers the right tool for each job.

Documentation patterns

Every component API needs documentation showing: the property name, its type (color, length, number), its default value, and an example of usage. This is the CSS equivalent of a TypeScript interface — it defines the shape of what consumers can control.

The inheritance chain

Custom properties inherit by default. A --btn-bg set on a parent container flows into all button descendants. This is both power and danger. Power: theme a section by setting properties on a wrapper. Danger: unintended leakage into nested components. Use @property registration with inherits: false to block inheritance when needed.

Versioning component APIs

Adding a new custom property to the API is a minor version bump (non-breaking — existing consumers are unaffected). Removing or renaming a property is a major version bump (breaking — existing consumers will lose their customization). Changing a default value is a patch if the visual difference is negligible, or a major if it significantly alters the component's appearance.

Anti-patterns

Exposing everything: If every internal value is a custom property, the API is too large to document and impossible to maintain. Internal padding ratios, computed hover colors, and animation timing curves should remain private.

Conflicting properties: Exposing both --btn-padding (shorthand) and --btn-padding-block / --btn-padding-inline (longhands) creates ambiguity. Pick one level of granularity. If you expose longhands, do not also expose the shorthand.

No defaults: A component that requires consumers to set custom properties to function is broken out of the box. Every API property must have a sensible default via the var(--prop, fallback) pattern.

Demo — Component with documented 8-property API

/* Button Component API */
--btn-bg: <color> = oklch(48% 0.18 275)
--btn-color: <color> = oklch(100% 0 0)
--btn-radius: <length> = 0.5rem
--btn-padding-block: <length> = 0.65rem
--btn-padding-inline: <length> = 1.25rem
--btn-font-size: <length> = 0.875rem
--btn-font-weight: <number> = 500
--btn-border-width: <length> = 0px

Real-world API documentation format

Document your component API as a comment block at the top of the component file. This serves the same purpose as JSDoc or TypeScript interfaces — it tells consumers what they can control without reading the implementation:

/*
 * Button Component API
 * ====================
 * --btn-bg           : <color>   = oklch(48% 0.18 275)  | Background color
 * --btn-color        : <color>   = oklch(100% 0 0)      | Text color
 * --btn-radius       : <length>  = 0.5rem               | Corner radius
 * --btn-padding-block  : <length> = 0.65rem             | Vertical padding
 * --btn-padding-inline : <length> = 1.25rem             | Horizontal padding
 * --btn-font-size    : <length>  = 0.875rem             | Font size
 * --btn-font-weight  : <number>  = 500                  | Font weight
 * --btn-border-width : <length>  = 0px                  | Border width
 *
 * Usage:
 *   .my-context .btn { --btn-bg: var(--my-brand-color); }
 */

This format is scannable, grep-friendly, and provides everything a consumer needs: the property name, its expected type, its default value, and its purpose. No implementation details exposed.

Mini-exercise

Add --btn-shadow to the API with a default of none. Then create a variant called .elevated that sets a subtle box-shadow using the API property. Notice how you added a new capability without modifying the base component implementation — that is the power of a well-designed API.
