Naming Conventions: BEM, CUBE, PE7 Compared

Every naming convention is a contract between developers. BEM encodes structure in the name itself. CUBE embraces the cascade. PE7 replaces naming conventions entirely with architectural layers. Understanding all three helps you choose the right tool for your team.

BEM: Block, Element, Modifier

BEM encodes the component hierarchy directly in class names. A .card__title--featured tells you the block (card), the element (title), and the modifier (featured) at a glance. The contract: every class is self-documenting.

Strengths

Explicit relationships between elements. Zero cascade dependency — specificity is flat by convention. Grep-friendly — you can find every usage of a block instantly. Easy onboarding for new developers who can read the HTML and understand the structure. Works without any build tool or modern CSS feature — pure convention.

Weaknesses

Verbose HTML. A complex component can require 15+ unique class names. No cascade awareness means duplication — shared styles between blocks must be extracted manually. Modifier explosion for complex states (responsive + theme + state = combinatorial naming). The naming becomes the architecture rather than the architecture informing the naming. Teams spend hours debating whether something is a block or an element.

BEM in practice

/* The BEM naming contract */
.card { }                    /* Block */
.card__title { }             /* Element */
.card__title--large { }      /* Modifier */
.card--featured { }          /* Block modifier */
.card--featured .card__title { } /* Contextual override */

CUBE CSS: Composition, Utility, Block, Exception

Andy Bell's CUBE CSS embraces the cascade instead of fighting it. Composition classes handle layout (.flow, .cluster, .sidebar). Utility classes handle single-purpose overrides (.text-center, .gap-lg). Block classes handle component-specific styling. Exceptions handle state with data attributes ([data-state="active"]).

Strengths

Cascade-friendly — works with the browser rather than against it. Less HTML markup since composition classes are reusable. Leverages browser defaults and inheritance. Encourages design tokens via utility classes. The categorization (C-U-B-E) gives developers a mental model for where styles belong.

Weaknesses

Utility class proliferation can make HTML harder to read. Less explicit than BEM for large teams where multiple developers touch the same components. Requires cascade understanding that junior developers may lack. The line between "composition" and "utility" is sometimes unclear.

CUBE in practice

/* Composition — layout primitives */
.flow > * + * { margin-block-start: var(--flow-space, 1em); }
.cluster { display: flex; flex-wrap: wrap; gap: var(--cluster-gap, 1rem); }

/* Utility — single-purpose overrides */
.text-center { text-align: center; }
.bg-primary { background: var(--color-primary); }

/* Block — component-specific */
.card { border-radius: var(--radius-md); padding: var(--space-lg); }

/* Exception — state via data attributes */
.card[data-state="featured"] { border-color: var(--color-primary); }

PE7: Layers + @scope + Custom Properties

PE7 eliminates naming conventions as a concern entirely. With @layer controlling specificity order, @scope controlling reach, and custom properties providing the component API, the architecture itself prevents conflicts. You name things descriptively — for humans — without needing to encode hierarchy or specificity information in the name.

Strengths

Zero naming convention overhead — no team meetings about naming rules. Architecture replaces discipline — you cannot accidentally break specificity because layers enforce order. Cascade is controlled by the browser, not by developer agreement. Scales infinitely without naming collisions because @scope provides true encapsulation. Components use semantic HTML selectors internally.

Weaknesses

Requires modern browser support (@layer is broadly supported, @scope is newer). Steeper learning curve for the architecture itself — developers must understand layers, scope, and custom property inheritance. Less established community consensus compared to decade-old BEM. Tooling ecosystem is still maturing.

PE7 in practice

/* Layer order declared once — this IS the architecture */
@layer tokens, reset, base, layouts, components, utilities;

/* Components use @scope — no naming convention needed */
@layer components {
  @scope (.card) {
    :scope { border-radius: var(--radius-md); padding: var(--space-lg); }
    h2 { font-size: var(--text-lg); }
    footer { border-top: 1px solid var(--border-color); }
  }
}

Side-by-side: the same card component

Consider a card with a title, body text, a footer with two actions, and a "featured" state. In BEM: .card, .card__title, .card__body, .card__footer, .card__action, .card__action--secondary, .card--featured. Seven classes for one component. In CUBE: .card (block), .flow (composition for spacing), [data-state="featured"] (exception). Three or four classes. In PE7: <article class="card"> with internal elements styled by @scope using semantic HTML selectors. One class for the scope root.

The real cost of each approach

BEM's cost is markup verbosity and class name management. As a codebase grows to 500+ components, the naming discipline becomes the bottleneck — developers spend time debating names rather than building features. CUBE's cost is requiring cascade literacy from every team member. PE7's cost is requiring modern browser support and understanding of @layer/@scope — but once understood, the naming question disappears entirely.

When each is appropriate

BEM: Legacy codebases, teams with mixed CSS skill levels, projects requiring IE11 support, brownfield projects where consistency with existing code matters more than architectural purity.

CUBE: Small-to-medium teams that understand the cascade, projects with a strong design token system, teams that value minimal HTML markup and embrace utility-first patterns.

PE7: New projects targeting modern browsers, teams ready to invest in architectural understanding over naming discipline, design systems that need to scale across multiple consuming applications without conflicts.

Migration path between conventions

Moving from BEM to PE7 is incremental: wrap BEM classes in a @layer legacy, write new components with @scope, and migrate existing components one at a time. The BEM classes continue to work inside the legacy layer — no big-bang rewrite needed. This is covered in detail in Lesson 22.6.
