Lesson 22.7 · Enterprise Architecture

Building a Design System CSS Package

A design system CSS package is infrastructure: consumed by multiple applications, versioned with semver, and integrated via @layer so it can never accidentally override application styles. Here is how to build one that scales.

File structure for a distributable package

design-system/
  main.css          (entry point with @layer declaration)
  tokens/
    colors.css
    spacing.css
    typography.css
  reset/
    reset.css
  base/
    base.css
  components/
    button.css
    card.css
    badge.css

The entry point (main.css) declares layer order and imports everything. Consumers import only this file.

The entry point

/* main.css */
@layer system.tokens, system.reset, system.base, system.components;

@import url("./tokens/colors.css") layer(system.tokens);
@import url("./tokens/spacing.css") layer(system.tokens);
@import url("./tokens/typography.css") layer(system.tokens);
@import url("./reset/reset.css") layer(system.reset);
@import url("./base/base.css") layer(system.base);
@import url("./components/button.css") layer(system.components);
@import url("./components/card.css") layer(system.components);
@import url("./components/badge.css") layer(system.components);

What to include and exclude

Include: tokens (the design language), reset (consistent baseline), base (typography, link styles), components (reusable UI patterns). Exclude: layout (that is application-level), animations (application-specific motion), page-specific overrides (that is consumer territory).

Consumer integration

/* app.css */
@layer system, app.layouts, app.components, app.utilities;

@import url("design-system/main.css") layer(system);

By importing the entire design system into a single system layer, all application layers automatically have higher priority. The design system provides defaults; the application overrides freely. No !important needed, no specificity battles. This is why @layer makes design systems safe.

Versioning with semver

Patch (1.0.x): value adjustments within existing tokens. Minor (1.x.0): new tokens, new components, new API properties. Major (x.0.0): removed tokens, renamed APIs, breaking structural changes. Every major version bump requires a migration guide.
