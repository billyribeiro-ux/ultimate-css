Lesson 22.3 · Enterprise Architecture

Multi-Theme Architecture

Supporting two themes is manageable. Supporting four or more demands architecture. The data-attribute pattern, token aliasing, and a strict file structure let you add themes without touching a single component file.

The data-attribute pattern

Themes are activated via [data-theme="name"] on a root element. Each theme defines the same set of semantic tokens with different values. Components reference only semantic tokens, never raw colors. This decoupling means zero component changes when a new theme is added.

Token aliasing at the theme level

A two-tier token system: primitive tokens (the raw palette: --blue-500) and semantic tokens (the meaning: --color-surface, --color-on-surface). Themes reassign semantic tokens to different primitives. Components only use semantic tokens.

Theme-specific overrides without duplication

If a component needs different spacing or border-radius in a specific theme, the override lives in the theme token file, not in the component. The component reads var(--card-radius, 0.75rem). A theme that wants sharper cards sets --card-radius: 0.25rem at the theme level.

The theme file structure

One file per theme: theme-light.css, theme-dark.css, theme-ocean.css, theme-contrast.css. Each file contains only custom property declarations scoped to [data-theme="name"]. Zero selectors targeting elements or classes. Zero component-specific rules.

Runtime theme switching with :has()

Using :has() on a <select> element, themes can be switched with zero JavaScript. The selector :root:has(select[name="theme"] option[value="dark"]:checked) applies dark theme tokens when the dark option is selected. Pure CSS interactivity.
