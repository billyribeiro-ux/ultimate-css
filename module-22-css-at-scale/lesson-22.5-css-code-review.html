Lesson 22.5 · Enterprise Architecture

CSS Code Review Checklist

Code review is where architecture is enforced or eroded. A systematic checklist catches boundary violations, specificity escalation, and accessibility gaps before they reach production. Here is what to look for and how to communicate it.

The checklist

1. Layer boundary violations

Is the new CSS in the correct layer? A component style in the utilities layer, or a token definition inside a component file, signals an architectural boundary violation. The rule: each piece of CSS lives in exactly one layer, and that layer matches its purpose.

What to look for: @layer declarations in the wrong file, styles that affect elements outside their intended scope, utility-style rules (single-property overrides) inside component files, or component-style rules (multi-property blocks) inside utility files.

2. Hard-coded values

Any raw color, font-size, or spacing value that should reference a token is technical debt. Search for oklch(, #, rgb( outside the token layer. Search for pixel values that don't match the spacing scale. Each hard-coded value is a point where the system can drift.

Exception: values that are truly one-off and contextual (a specific animation offset, a clip-path coordinate) may be legitimately hard-coded. The test: would changing this value ever need to be coordinated with other components? If yes, it should be a token.

3. Specificity escalation

Are selectors unnecessarily specific? A .header .nav .link.active when .nav-link[aria-current] would suffice signals specificity inflation. With @layer, specificity within a layer only matters against other rules in that same layer — but unnecessary specificity still makes code harder to override and reason about.

Red flags: descendant selectors more than 2 levels deep, ID selectors in component CSS, qualifying class selectors with element types (e.g., button.btn instead of .btn), and chained classes that could be simplified.

4. Missing @supports

Does the code use modern features without fallback consideration? If the project supports older browsers, progressive enhancement via @supports should wrap newer features. Even in modern-only projects, @supports documents which features are load-bearing.

Check for: @scope, :has(), container queries, anchor positioning, subgrid — all features that may need graceful degradation depending on the browser support matrix.

5. Accessibility gaps

Focus styles present and visible? Color contrast sufficient (4.5:1 for normal text, 3:1 for large text)? Motion respects prefers-reduced-motion? Interactive elements have sufficient touch targets (44x44px minimum)? Text remains readable at 200% zoom? Content reflows properly at 320px viewport? These are not optional — they are requirements.

Additional checks: display: none hiding content that should remain accessible to screen readers (use .visually-hidden instead), color being the sole indicator of state (add an icon or text label), and custom focus styles that are less visible than the browser default.

6. Performance anti-patterns

Expensive selectors (* with complex combinators), forced reflows from layout-triggering properties in transitions (avoid animating width, height, top, left — use transform instead), excessive use of filter or backdrop-filter on large areas, and unused CSS that bloats the bundle. Each has a measurable cost at scale.

Also check: will-change applied permanently instead of on interaction, contain missing on components that would benefit from layout containment, and @font-face loading strategies that block rendering.

7. Naming and intent clarity

Even without strict BEM naming, CSS should communicate intent. A class called .x or .wrapper2 tells future developers nothing. A class called .product-grid or .auth-form is self-documenting. Custom properties should describe what they control, not their current value: --spacing-section not --24px.

The PE7 audit automated with grep

Automate the easy checks:

# Find hard-coded colors outside tokens layer
grep -rn "oklch\|#[0-9a-f]\{3,8\}" src/components/

# Find !important usage (usually a red flag)
grep -rn "!important" src/

# Find high-specificity selectors (3+ classes)
grep -rn "\.[a-z].*\.[a-z].*\.[a-z]" src/

# Find missing prefers-reduced-motion
grep -rL "prefers-reduced-motion" src/components/*animation*

How to give constructive CSS review feedback

The "why" matters more than the "what." Instead of "Don't use !important here," write "This !important will make it impossible for consumers to override this style via the component API. Consider using a @layer instead, which gives you priority without blocking future overrides."

Categorize feedback: blocking (must fix — accessibility, architecture violation), suggestion (would improve — naming, organization), nit (take it or leave it — formatting, preference). Be explicit about which category each comment falls into.

Common review patterns

The "works but wrong layer" pattern

The CSS achieves its visual goal but lives in the wrong architectural layer. This is the most common PE7 violation: a token defined inline in a component, or a layout rule embedded in a utility class. The fix is always a move, never a rewrite.

The "specificity arms race" pattern

A rule overrides another by adding specificity. The override is then overridden by adding more specificity. The cascade becomes a battleground. The fix: identify which layer each rule belongs in and let layer order do the work.

The "copy-paste component" pattern

A new component is created by copying an existing one and modifying it. The result: duplicated tokens, duplicated structure, diverging implementations. The fix: extract the shared API into custom properties and create variants, not copies.

The "magic number" pattern

Hard-coded values with no explanation: margin-top: 37px, width: 287px. These numbers encode implicit relationships. The fix: replace with a token or add a comment explaining the derivation. If the value derives from a calculation, make that calculation explicit with calc().

The "override chain" pattern

A series of selectors where each overrides the previous, creating a fragile chain where removing one rule breaks others downstream. The fix: flatten the cascade using layers so each rule operates independently without depending on being overridden.

Review examples: before and after

Example 1: Hard-coded color in a component

/* Before — hard-coded value */
.alert { background: oklch(92% 0.05 25); }

/* After — using a token */
.alert { background: var(--color-danger-surface); }

Review comment: "This color should reference the danger-surface token so it updates automatically with theme changes and stays in sync with other danger indicators across the app."

Example 2: Specificity escalation

/* Before — specificity arms race */
.sidebar .nav .link { color: blue; }
.sidebar .nav .link.active { color: darkblue; }
body .sidebar .nav .link.active.current { color: navy; }

/* After — layer-based priority */
@layer components {
  .nav-link { color: var(--nav-link-color); }
  .nav-link[aria-current="page"] { color: var(--nav-link-active); }
}

Review comment: "The selector specificity here is escalating to override prior rules. With @layer, simple selectors suffice because layer order provides the priority. This also makes the active state accessible via aria-current."

Example 3: Missing accessibility

/* Before — motion without preference check */
.hero { animation: slide-in 800ms ease; }

/* After — respects user preferences */
.hero { animation: slide-in 800ms ease; }
@media (prefers-reduced-motion: reduce) {
  .hero { animation: none; }
}

Review comment (blocking): "This animation runs unconditionally. Users with vestibular disorders can experience nausea from unexpected motion. Wrap in a prefers-reduced-motion check or use the motion-safe utility pattern."

Building a review culture

CSS reviews work best when the team agrees on principles before the first review. Document the architecture in an ADR (Module 22 Project). Share the checklist. Run lunch-and-learn sessions on common patterns. When everyone understands the why, reviews become collaborative rather than adversarial.

The goal is not zero review comments — it is reviewers catching things that automated tooling cannot: semantic correctness, user experience implications, and architectural intent. Automate what you can (see Lesson 22.8), review what requires human judgment.

Key takeaway

A CSS code review is not about personal style preferences. It is about enforcing the architecture that keeps the system maintainable. Every review comment should reference a principle (layer boundaries, token governance, accessibility requirements) — not a personal preference. When the review is principle-based, it is impersonal and actionable.
