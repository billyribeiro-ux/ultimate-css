Lesson 22.2 · Enterprise Architecture

Design Token Governance

A single color token change can cascade across thousands of pages. Token governance answers the hard questions: who owns the tokens, how do changes propagate, and what constitutes a breaking change?

Who owns the tokens?

In enterprise teams, token ownership typically lives with the design system team. Product teams consume tokens but do not modify them. Changes require a review process because a token change is fundamentally a global change: updating --color-primary touches every component that references it.

The review process

Token changes follow a stricter process than component changes. The minimum viable process: (1) proposal with visual impact screenshots, (2) design review, (3) engineering review for accessibility and performance, (4) staged rollout with feature flags. A color change that fails WCAG contrast in even one context is a blocking issue.

Versioning tokens with semver

Tokens follow semantic versioning. Patch: adjusting a value within its existing role (shifting a blue by 2% lightness). Minor: adding new tokens. Major: removing tokens, renaming tokens, or changing a token's semantic meaning.

Breaking vs non-breaking changes

A breaking change is any modification that requires consumers to update their code: renaming a token, removing a token, or changing a token's type (color to gradient). A non-breaking change adjusts the value while preserving the contract: the token still represents what it always represented.

The token audit

Periodically audit the codebase for hard-coded values that should be tokens. A grep for hex colors, raw pixel values, or oklch() calls outside the token layer reveals governance failures. Every hard-coded value is technical debt that bypasses the system.

Brand Colors

--color-primary oklch(48% 0.18 275) Buttons, links, focus rings
--color-secondary oklch(55% 0.15 320) Accents, badges, highlights
--color-success oklch(62% 0.17 145) Confirmations, positive states
--color-warning oklch(75% 0.15 80) Alerts, caution states
--color-danger oklch(55% 0.2 25) Errors, destructive actions

Neutral Scale

--neutral-100 oklch(97% 0.005 275) Page backgrounds
--neutral-300 oklch(85% 0.01 275) Borders, dividers
--neutral-700 oklch(35% 0.02 275) Body text
--neutral-900 oklch(15% 0.02 275) Headings, emphasis

Try it yourself

Mini-exercise

Add a "deprecated" badge to one of the spacing tokens. Style it with oklch(55% 0.2 25) background. Then add a replacement token below it showing the migration path. This is how token documentation communicates breaking changes during a major version transition.
