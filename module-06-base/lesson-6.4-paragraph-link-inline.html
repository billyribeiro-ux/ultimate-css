Lesson 6.4

Paragraph, Link, and Inline Text

Prose is the hardest thing to style well because every decision compounds across thousands of words. Four small rules — a measure, a wrap mode, a decoration thickness, and an underline offset — make the difference between prose that reads and prose that tires the eye.

Measure: 65ch

The "measure" is the width of a line of text. Typographic research converges on 60-75 characters as the sweet spot — shorter lines fatigue the eye with too many line breaks, longer lines lose the reader on the return sweep. The PE7 base sets the measure on every prose element, not on a wrapper class:

p {
  max-inline-size: var(--measure); /* e.g. 65ch */
  text-wrap: pretty;
  color: var(--color-text-secondary);
}

Setting it as a token means any layout can widen or narrow the measure globally for translation purposes — German prose, for example, runs longer than English and sometimes benefits from a 70ch measure.

text-wrap: pretty

Where balance optimises a small number of lines for visual evenness, pretty optimises a large number of lines to avoid bad line endings — short last lines, orphaned words, hyphenation clashes. It costs more to compute than default wrapping but the difference in legibility is visible on any page with more than a few paragraphs. Use it on p, not on headings.

Links: the underline is a signal

Default browser underlines sit on the baseline, cross descenders, and are one pixel thick regardless of font size. Three properties fix all three problems:

a {
  color: var(--color-link);
  text-decoration: underline;
  text-decoration-thickness: 1px;
  text-underline-offset: 3px;
}
a:hover {
  color: var(--color-link-hover);
  text-decoration-thickness: 2px;
}

text-underline-offset pushes the underline below the baseline so descenders on "g" and "y" pass above it. text-decoration-thickness scales with font metrics rather than device pixels. On hover the thickness doubles — a subtle affordance that does not rely on color alone, which matters for users with color vision deficiency.

Inline text elements

strong, b { font-weight: var(--weight-bold); color: var(--color-text-primary); }
em, i     { font-style: italic; }
small     { font-size: var(--size-sm); color: var(--color-text-tertiary); }
code, kbd, samp {
  font-family: var(--font-mono);
  font-size: 0.9em;
  padding-inline: 0.3em;
  padding-block: 0.1em;
  background-color: var(--color-code-bg);
  border: 1px solid var(--color-code-border);
  border-radius: var(--radius-sm);
}

strong gets a color promotion as well as weight — this counters the visual "disappearance" of bold text against a grey paragraph color. Inline code uses 0.9em rather than a fixed size so it always tracks the surrounding text.

Why 0.9em and not var(--size-sm)?

Inline code is relative to its container, not to a global size. A code inside an h2 should scale with the heading; a code inside a p should scale with prose. 0.9em achieves both; a token reference would force you to pick one. This is the only place in base where a non-token value is acceptable — and it is still relative.

Try it yourself

Mini-exercise

Set --measure to 200ch and read the paragraph. Try to finish one sentence without losing your place on the return sweep. Now set it to 30ch. Notice how both extremes slow you down. Somewhere between 60 and 75 is the comfort zone for English prose — the default token value is deliberately inside that range.
