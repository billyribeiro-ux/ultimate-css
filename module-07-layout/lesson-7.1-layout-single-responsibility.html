Lesson 7.1

Layout's Single Responsibility

Every layout primitive answers exactly one question, and it never answers any other. This rule is what makes six small classes enough to build any real layout, and it is what makes layout CSS the most portable part of a PE7 stylesheet.

What layout does

Layout decides the spatial relationship between children. Vertical or horizontal, one column or many, wrap or overflow, centred or aligned, near or far. Those are layout's questions. Everything else — colors, shadows, fonts, borders — is a component's question.

The six primitives

Six classes cover the vast majority of production layouts. They are deliberately few, deliberately boring, and deliberately composable.

  1. container — "constrain inline width and centre inside the viewport."
  2. stack — "vertical flow with consistent gap."
  3. cluster — "horizontal flow that wraps when there is not enough room."
  4. sidebar — "a fixed-basis column next to a flexible column, collapsing to one column below a threshold."
  5. grid — "responsive columns that fit as many items as possible."
  6. cover — "full-viewport-height centred content."

Composition, not specialisation

Every complex layout you need is a composition of these primitives. A documentation page is a container > stack. A product listing is a container > stack > grid. A blog article is a container > sidebar > stack + stack. When you find yourself writing a new layout class for a specific page, you are specialising — and specialisation is almost always a composition you have not spotted yet.

The anti-pattern: component-level layout

A .card that writes its own display: grid; grid-template-columns: 1fr 2fr; is a component doing layout work. That is the anti-pattern this module exists to kill. When a card contains a layout, the layout should be a primitive class on a child element, not a rule on the card itself:

<!-- Wrong: card does layout -->
<div class="card">
  <img ...>
  <div>
    <h3>Title</h3>
    <p>Body</p>
  </div>
</div>

<!-- Right: card is visual, layout is composed -->
<div class="card sidebar">
  <img ...>
  <div class="stack">
    <h3>Title</h3>
    <p>Body</p>
  </div>
</div>

The "right" version reuses .sidebar and .stack — two layout primitives the rest of the page is already using. No special CSS is added for this particular card.

Why zero visual opinions

If .stack sets a background color, you cannot use it on a light section and a dark section. If .grid sets a font, you cannot use it inside a heading and a body. The moment a layout primitive has a visual opinion, it stops being reusable. Reusability is the entire point.

Interface as custom properties

Each primitive exposes its knobs as custom properties with sensible defaults:

.stack { --stack-gap: var(--space-md); gap: var(--stack-gap); }
.stack-lg { --stack-gap: var(--space-xl); }

/* Consumer can also set it inline, or from a component */
.hero > .stack { --stack-gap: var(--space-2xl); }

The component layer never overrides the primitive's property directly — it sets a custom property, and the primitive picks it up. This is the same contract pattern we introduced for buttons in Module 3.

Try it yourself

Mini-exercise

Open any component in your last project. List every CSS property on that component. Cross out every property that is about visual appearance (color, font, shadow, border). What remains is layout. If what remains is more than two or three properties, that component has a layout primitive inside it waiting to be extracted.
