Lesson 7.9

The Columns Primitive: CSS Multi-Column

One layout method has been missing from this module: multi-column. Grid and flex arrange discrete items; multicol fragments continuous content — one stream of text flowing down a column and continuing at the top of the next, like a newspaper. It is the right tool for exactly that job, the wrong tool for almost everything else, and fully production-ready everywhere.

Continuous vs. discrete — the mental model

The root distinction: grid and flex are item-placement models — each child is an atomic box assigned to a slot. Multicol is a fragmentation model — the container's entire content is treated as one continuous flow, sliced into column boxes, the same machinery that paginates content for print. A paragraph can start at the bottom of column one and finish at the top of column two. That is the superpower and the trap in one sentence: text should flow across a break; a card never should. Choose multicol when the content is prose, a long list, or anything you would happily see split mid-element in a newspaper.

column-width: the responsive way

There are two ways to ask for columns, and they differ in who does the responsive math:

/* You fix the count — YOU now own every viewport's layout */
.columns { column-count: 3; }

/* You state the ideal width — the BROWSER derives the count */
.columns { column-width: 20rem; }

/* Shorthand: 'columns'. With both, count acts as a maximum */
.columns { columns: 20rem; }
.columns { columns: 3 20rem; }  /* ≤3 columns, each ≥20rem */

column-count: 3 means three columns at every width — sixty-character lines on a desktop monitor, six-character lines on a phone, until you patch it with media queries. column-width: 20rem means "columns of about 20rem, as many as fit": the browser computes floor(available / ideal), never fewer than one, and stretches the columns to fill the remainder. The container reflows from one column to four as space changes with zero media queries — the same self-deciding instinct as the grid primitive's auto-fit, minmax() from Lesson 7.6, applied to flowing text. This is the module's whole philosophy, so column-width is the primitive's interface; column-count is the special case.

column-gap and column-rule

column-gap is the same property grid and flex use (multicol is where it originated; default here is 1em, not normal-as-zero). column-rule draws a divider in the middle of each gap — and crucially it is painted, not laid out: it occupies no space and cannot affect column sizing.

.columns {
  column-width: 20rem;
  column-gap: 2.5rem;
  column-rule: 1px solid oklch(85% 0.01 264);
  /* longhands: column-rule-width / -style / -color */
}

Until recently multicol was the only layout that could decorate its gaps. The 2026 gap-decorations work generalizes exactly this property family — column-rule and the new row-rule — to grid and flex containers; Lesson 13.24 covers it. Learn the syntax here and you have already learned it there.

column-span: breakout headings

An element inside the flow can interrupt the columns and span the full container width — the classic newspaper headline. Content before it fragments into columns above; content after it starts a fresh column row below:

.columns h2 {
  column-span: all;     /* only 'all' or 'none' — no partial spans */
  margin-block: 1.5em 0.75em;
}

column-fill: balance vs. auto

When the container's block size is unconstrained (the normal case), columns are always balanced — the browser minimizes height so columns come out near-equal, and column-fill is moot. It matters when you constrain the height: balance (the initial value) still equalizes content across columns; auto fills each column to the brim before starting the next, which can leave later columns empty. Use auto for fixed-height "teleprompter" panes that scroll horizontally; keep balance everywhere else.

.ticker {
  block-size: 16rem;     /* constrained height activates the choice */
  columns: 18rem;
  column-fill: auto;     /* fill sequentially, overflow inline-ward */
}

Fragmentation control

Because multicol shares the print fragmentation engine, it obeys the same control properties. break-inside: avoid keeps an element from being sliced across a column boundary; orphans and widows (Lesson 6.8 set them in the base layer for exactly this moment) set the minimum lines of a paragraph allowed on either side of a break:

.columns :is(figure, blockquote, li) { break-inside: avoid; }
.columns p { orphans: 3; widows: 3; }     /* no stranded lines */
.columns h3 { break-after: avoid; }       /* heading stays with text */

The classic pitfalls — why multicol is wrong for cards

Every few years a team rediscovers columns as a "free masonry" for card grids, and the same three failures follow. First, cards get sliced mid-element at column breaks unless every card carries break-inside: avoid — and even then, balancing produces ragged column bottoms you cannot control. Second, reading order runs down each column: items 1-2-3 stack vertically in column one, so chronological feeds read top-to-bottom-then-back-up — disorienting visually, and doubly so for keyboard and screen-reader users on long containers where "next item" means scrolling back to the top. Third, items cannot be reordered, spanned, or aligned — there is no placement model, because there are no slots. Lesson 16.5's portfolio gallery uses masonry-via-columns deliberately and documents these exact trade-offs; the grid-lanes masonry from Lesson 7.8 is the placement-aware answer for discrete items. The rule: cards are discrete → grid; prose is continuous → columns.

Where multicol earns its keep in production

Beyond article prose, the highest-value uses are long lists — content that is technically itemized but reads as one continuous stream, where a mid-list column break is harmless because each item is short:

/* A footer sitemap or A–Z index: 60 links, no scrolling forever */
.footer-links ul {
  columns: 11rem;
  column-gap: 2rem;
}
.footer-links li { break-inside: avoid; }  /* links never split */

/* A long checkbox group in a settings form */
.permissions fieldset {
  columns: 14rem;
}
.permissions label { display: block; break-inside: avoid; }

The pattern in both: items are a single line or two, so break-inside: avoid costs nothing, and the column count adapting to the container is pure win. Reading order still runs down each column — fine for an alphabetized index a user scans, wrong for a ranked list a user reads in order. That distinction, not the markup, is what decides. One more production note: a column box establishes a containing block for its content but columns themselves are anonymous — you cannot select or style "column two", only the rule between columns. If a design requires per-column treatment, the content is discrete and belongs in grid.

The PE7 primitive

Like every primitive in this module, .columns is structure only — a custom-property interface, no visual styling, single responsibility:

@layer layout {
  .columns {
    columns: var(--column-width, 20rem);
    column-gap: var(--column-gap, var(--grid-gap, 1.5rem));
  }
  .columns > :is(figure, blockquote) { break-inside: avoid; }
}

/* Usage: structure from the primitive, theme at the call site */
<section class="columns" style="--column-width: 16rem">
  <p>…flowing prose…</p>
</section>

Support: everything in this lesson — columns, column-gap, column-rule, column-span, column-fill, break-inside — is production, supported across all engines for years. No @supports, no fallback. The only thing to gate is your own judgment about continuous vs. discrete content.

Demo — flowing prose with a spanning headline

Resize the browser: the column count re-derives itself from column-width with no media queries — one column when narrow, three or four when wide. The heading spans all columns, the rule marks the gaps, and break-inside: avoid keeps the quote intact.

The browser derives the count

This container declares only an ideal column width. The number of columns is computed from the available space — as many 14rem columns as fit, stretched to share the remainder. Narrow the window and the count drops; widen it and columns appear.

Text flows continuously: this paragraph may begin at the bottom of one column and finish at the top of the next, exactly as a newspaper sets it. That mid-element break is the defining behavior of a fragmentation layout.

This quote carries break-inside: avoid, so it always moves to the next column whole rather than being sliced at the boundary.

The vertical line between columns is a column-rule. It is painted in the gap rather than laid out, so it takes no space — and it only appears where two columns actually meet.

No media query and no container query appears anywhere in this demo. The layout re-decides itself at every width, which is this module's measure of a well-built primitive.

Try it yourself

Mini-exercise

Prove the continuous-vs-discrete rule to yourself. (1) Add the .columns primitive to your layout layer with the --column-width interface and pour a long article into it — confirm the count adapts as you resize, with no queries. (2) Now pour six cards into the same container and watch them get sliced at column boundaries; add break-inside: avoid and observe the ragged, unordered result — then move the cards to the grid primitive from Lesson 7.6 and note how much better discrete items behave in a placement model. (3) Finally, add a column-span: all heading mid-article and a column-rule, and tab through the article with the keyboard to confirm that for prose, focus and reading order remain perfectly sensible — the right content in the right primitive.
