Lesson 7.7

Container Queries & Style Queries

Media queries ask "how wide is the viewport?" — but a component does not live in a viewport, it lives in a container. Container queries ask the correct question: "how wide am I?" The same card shown in a sidebar and a full-width grid can use one CSS file and still look right in both.

The viewport-aware anti-pattern

Media queries are blunt. A card that becomes a two-column layout at @media (min-width: 40rem) is correct when the card is full-viewport-width on a 40rem screen, and wrong when the same card is crammed into a 20rem sidebar on an 80rem screen. The component's layout depends on the component's box, not the browser's box.

Container queries: two steps

Container queries require two CSS rules — one to declare the container, one to query it.

.card {
  container-type: inline-size;
}

@container (inline-size >= 30rem) {
  .card .content {
    display: grid;
    grid-template-columns: 1fr 2fr;
  }
}

container-type: inline-size tells the browser to track this element's inline size and make it queryable. @container (inline-size >= 30rem) applies its rules when the nearest ancestor container reaches that size. No media query, no viewport dependence, no breakpoint list.

container-name for disambiguation

When components nest — a card inside a card — you often want to query a specific ancestor, not the nearest one. Name your containers:

.card      { container: card / inline-size; }
.article   { container: article / inline-size; }

@container article (inline-size >= 50rem) { ... }
@container card    (inline-size >= 30rem) { ... }

The shorthand container: name / type sets both container-name and container-type.

Component-aware, not viewport-aware

The same card now renders differently when embedded in a wide grid cell versus a narrow sidebar cell — automatically, with one CSS file. You do not have to know where the card will be used to write its CSS. This is the property that media queries can never give you.

Style queries

Container queries can also query custom property values, not just sizes. A style query matches when a specific custom property on the container has a specific value.

.layout { --layout: grid; }

.layout[data-sidebar] { --layout: sidebar; }

@container style(--layout: sidebar) {
  .item { display: flex; }
}
@container style(--layout: grid) {
  .item { display: block; }
}

Style queries let a component change its layout based on a parent's declarative mode — without JavaScript and without class toggles on every descendant. Browser support is younger than size queries; wrap in @supports (container-type: inline-size) and ... if you need fallbacks.

Container query units

Inside a container, you can use cqi (container query inline size) as a length unit — font-size: 5cqi scales with the container, not the viewport. Useful for hero text inside components that need to respond to container width. Think of cqi as "per-cent of container inline size."

Mini-exercise

Resize the preview. Notice that the two cards flip from stacked to side-by-side at different times, because each one's container reaches 22rem at a different moment. That is component-aware responsiveness. Then remove container-type: inline-size — the @container block stops matching, and both cards revert to stacked layout regardless of their width. The container declaration is what activates the query.
