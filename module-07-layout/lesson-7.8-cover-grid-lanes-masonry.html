Lesson 7.8

Cover, Grid-Lanes, and Masonry

Two more primitives round out the layout vocabulary. Cover is a full-height centred container for hero sections and splash screens. Grid-lanes masonry is the native CSS answer to Pinterest-style staggered grids — still early in browser support, so it ships behind an @supports fallback.

The cover primitive

.cover {
  display: grid;
  place-items: center;
  min-block-size: var(--cover-min-height, 100svh);
  padding: var(--space-xl);
}

Three decisions: grid with place-items: center for unambiguous two-axis centring; 100svh for small-viewport-height (which excludes the mobile browser chrome, unlike 100vh); generous padding so content never touches the edges.

Why 100svh, not 100vh

On mobile Safari and Chrome, 100vh refers to the viewport height without the address bar — so a full-viewport hero is taller than the visible area on first load. When the user scrolls and the address bar collapses, the layout jumps. 100svh refers to the small viewport height — the smallest viewport will ever be during the session — so the hero never needs to resize. There is also lvh (large) and dvh (dynamic) for other use cases.

Cover with headlined content

Cover centres exactly one thing by default. If you need a headline plus a sub-headline plus a call-to-action, wrap them in a stack inside the cover:

<section class="cover">
  <div class="stack" style="--stack-gap: 1.5rem; text-align: center;">
    <h1>Hero headline</h1>
    <p>Tagline</p>
    <a class="btn" href="#">Call to action</a>
  </div>
</section>

Masonry via grid-lanes

Masonry is the Pinterest-style staggered grid where items flow into whichever column has the most space. Historically it required JavaScript. CSS Grid Level 3 adds a native masonry mode through grid-template-rows: masonry (Firefox) and the newer item-flow: row / column / grid-template-rows proposal. The syntax is still stabilising.

.masonry {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(12rem, 1fr));
  grid-template-rows: masonry;
  gap: var(--grid-gap, 1rem);
}

Masonry support is not universal. Wrap it in a feature query and fall back to a regular grid where the declaration is not recognised:

.masonry {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(12rem, 1fr));
  gap: 1rem;
}

@supports (grid-template-rows: masonry) {
  .masonry { grid-template-rows: masonry; }
}

Browsers without masonry see a regular fitted grid — all items the same row height, which is a perfectly fine fallback. Browsers with masonry see the staggered layout. No feature detection in JavaScript, no polyfill, no complexity.

Why these are the last two primitives

Six primitives (container, stack, cluster, sidebar, grid, cover) cover 99% of layouts. Masonry is a specialised grid variant for a specific visual style. Cover is a specialised centring primitive for hero sections. They do not need to be separate classes in every project — add them when you need them, and only then.

In a browser that does not, they render as a regular grid with uniform rows.
