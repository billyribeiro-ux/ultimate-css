Lesson 2.5

Unlayered Styles and the Escape Hatch

There is one kind of rule that beats every layer you will ever declare. It is not a bug. It is the feature that lets you adopt @layer on a legacy codebase without rewriting every file first.

The rule

Any CSS rule that is not inside an @layer block is "unlayered." Unlayered rules win against every layered rule — no matter what layer, no matter how high the priority, no matter how specific.

Read that twice. It sounds backwards. Intuitively, unlayered feels like "no priority," and no priority should be weak. In the spec, it works the other way: unlayered means "I am explicitly not participating in the layer system, so treat me as the final word."

Why that choice was made

If the spec had said "unlayered is weakest," then adding a single @layer components { ... } block to an existing project would instantly break every rule outside it. Adoption would be catastrophic. By making unlayered strongest, a pre-layer codebase keeps working exactly as before, and you can wrap subsystems in layers one at a time without regressions.

How to use it in practice

Unlayered is for exactly two things: a legacy codebase you are migrating into layers gradually, and genuine last-resort overrides that must win regardless of architecture. In a greenfield PE7 project, you should have zero unlayered rules. Every rule lives in a named layer. That discipline is what makes the cascade predictable.

The ordering, complete

  1. Unlayered rules — win against everything layered.
  2. Layered rules — ordered by layer declaration (last declared wins).

Both of those still sit under specificity for ties inside the same group.
