Lesson 13.24

Gap Decorations: Rules Between Grid & Flex Tracks

"Put a thin line between these items" has been a one-sentence design request and a multi-hour CSS problem for a decade. The CSS Gap Decorations module finally answers it directly: column-rule and the new row-rule now apply to grid and flex containers, drawing dividers inside the gaps you already have — with zero layout change.

The decade-old problem, and why every hack breaks

The root cause is simple: gaps are empty space, and CSS had no property that paints into that space. So we decorated the items instead — and every workaround fails for a structural reason, not a stylistic one:

  • Borders on items (li + li { border-inline-start: 1px solid }). Works for a single row. The moment the container wraps, the sibling combinator cannot know which item starts a new row — the first item of row two still has a left border, now floating at the row's leading edge. Shared edges double up to 2px, and the border participates in layout, so toggling it shifts content.
  • Background showing through the gap (container background + opaque item backgrounds). The "rule" is as thick as the entire gap — you cannot draw a 1px line inside a 24px gap without collapsing the gap to 1px. It cannot be dashed or partial, and any container padding paints the divider color around the outer perimeter too, framing the whole component in your divider color.
  • Pseudo-element separators (absolutely positioned ::before lines). These encode the column count into :nth-child() math. The instant repeat(auto-fit, …) or a viewport change alters the count, the separators land in the wrong places. They are decorations guessing at layout instead of reading it.

Multicol never had this problem — column-rule has painted lines between columns since CSS3. The fix was always obvious: extend that primitive to the layouts we actually use.

The fix: rules that live in the gap

The CSS Gap Decorations module does exactly that. The column-rule family now applies to grid and flex containers, joined by a symmetric row-rule family for the other axis. Each is a shorthand over three longhands, mirroring border:

.dashboard {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(12rem, 1fr));
  gap: 2rem;

  /* vertical lines between columns */
  column-rule: 1px solid oklch(88% 0.02 270);
  /* horizontal lines between rows */
  row-rule: 1px dashed oklch(88% 0.02 270);
}

/* Longhands, exactly like border:
   column-rule-width / column-rule-style / column-rule-color
   row-rule-width    / row-rule-style    / row-rule-color   */

Because the browser is painting from its own layout data, the rules are correct by construction: between tracks, never at the container edge, regardless of how many tracks auto-fit produces today.

Extent control: outset, break, and paint order

Three companion properties govern how far each rule extends and what happens where row and column rules cross:

.grid {
  /* Where does a rule break?
     none            → one continuous line across the whole axis
     spanning-item   → breaks around items that span tracks
     intersection    → a separate segment per gap intersection */
  column-rule-break: intersection;
  row-rule-break: spanning-item;

  /* How far past the item edges does each segment extend?
     50% (initial) → halfway into the crossing gap, so
     perpendicular rules meet cleanly; 0 stops flush with
     item edges; negative values pull segments shorter. */
  column-rule-outset: 0;
  row-rule-outset: 50%;

  /* Which rule paints on top where they cross? */
  rule-paint-order: row-over-column;  /* or column-over-row */
}

This is the difference between a spreadsheet (continuous rules, none) and a card wall (per-cell segments, intersection) — one property, not a rewrite.

Rules render inside the gap — no layout change

This is the property family's most important production characteristic: gap rules are pure paint. They are centered within the gap, they consume no space, and they do not alter track sizing, item position, or scroll dimensions. gap: 2rem with a rule is byte-for-byte the same layout as gap: 2rem without one. That makes them the rare feature that is progressive enhancement by physics, not by discipline — turning them off cannot shift a single pixel of content.

Worked patterns

The wrapping toolbar — the classic killer case. Separators between items within a row, a hairline between wrapped rows, and nothing at the edges. Notice there is no :nth-child() anywhere; the browser knows where the rows are because it made them:

.toolbar {
  display: flex;
  flex-wrap: wrap;
  gap: 0.5rem 1.5rem;
  column-rule: 1px solid var(--color-border);
  row-rule: 1px solid var(--color-border);  /* appears ONLY when it wraps */
}

The pricing table — vertical rules between plans, no rule trailing the last column:

.pricing {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
  gap: 0 3rem;
  column-rule: 1px solid oklch(90% 0.02 275);
}

The dashboard — subtle horizontal rhythm between widget rows, broken per intersection so each card reads as its own region:

.widgets {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(16rem, 1fr));
  gap: 1.5rem;
  row-rule: 1px solid oklch(92% 0.01 270);
  row-rule-break: intersection;
  row-rule-outset: 0;
}

Multicol today: train your hands now

The syntax is not speculative — column-rule has worked on columns-based multicol layouts in every engine for over a decade (Lesson 7.9 covers the multicol primitive in depth). Gap Decorations is deliberately an extension of that primitive, not a new invention: same shorthand shape, same longhands. Patterns you write for multicol article layouts today are the same muscle memory you will use on grid and flex tomorrow.

Shipping policy: learn and watch

This feature is Experimental tier, so the PE7 rule is absolute: the layout must be fully acceptable with no rules at all, and the rules ship only inside an @supports gate. One precision matters here — do not gate on column-rule-color. That property has parsed in every engine since multicol shipped, so the test is a false positive everywhere. Gate on the genuinely new syntax, row-rule:

/* Base layout: complete and shippable on its own */
.toolbar {
  display: flex;
  flex-wrap: wrap;
  gap: 0.5rem 1.5rem;
}

/* Enhancement: parsed only where Gap Decorations exists */
@supports (row-rule: 1px solid red) {
  .toolbar {
    column-rule: 1px solid var(--color-border);
    row-rule: 1px solid var(--color-border);
  }
}

Because rules are paint-only, there is no fallback "hole" to fill — non-supporting browsers simply see clean gaps. Resist the urge to polyfill with the border hacks above; you would be reintroducing the exact bug classes this feature retires.

Browser support

Experimental. Chrome 149 (June 2026) ships grid and flex gap decorations; Firefox and Safari have signalled positive positions but have not shipped. column-rule on multicol remains production-ready everywhere. Ship gap rules on grid/flex only behind the @supports (row-rule: …) gate shown above, and re-check support before promoting it to a default.

Demo — Gap rules behind @supports, honest in any browser

In a browser with Gap Decorations, the stat panel gets column and row rules and the toolbar grows a hairline between wrapped rows. Everywhere else, an @supports not (…) rule reveals a notice and you see the untouched fallback layout — which is the whole point: it is fully presentable on its own.

This browser does not support gap decorations yet — you are seeing the un-decorated fallback layout, which is exactly what users would get in production.

Mini-exercise

Rebuild the wrapping toolbar from this lesson with old-school hacks first: try button + button { border-inline-start: 1px solid } and resize until it wraps — note the orphaned border at the start of row two. Then delete the hack and add column-rule + row-rule inside an @supports (row-rule: 1px solid red) block. Finally, toggle the @supports block on and off in DevTools and verify the layout does not shift by a single pixel — gap rules are paint, not layout.
