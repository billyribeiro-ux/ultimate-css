Lesson 13.25

CSS Houdini: The Paint API & Typed OM

Houdini is the umbrella name for the APIs that open the browser's styling pipeline to JavaScript — letting you register typed properties, paint custom backgrounds, and manipulate styles as numbers instead of strings. This lesson is an honest status report: one piece of Houdini you have used all course without knowing it, one piece worth learning with a strict fallback discipline, and two pieces that quietly stalled.

Houdini: opening the styling pipeline

Normally CSS is a black box: you hand the engine declarations, it parses, cascades, lays out, and paints. Houdini exposes hooks into those stages. The Properties & Values API hooks parsing (custom properties with real types). The Paint API hooks painting (your code draws wherever CSS expects an image). The Layout and Animation Worklet APIs were meant to hook layout and compositing. The promise was "polyfill the future in user-space"; the reality, eight years on, is more selective — and a principal engineer plans around the reality.

The honest status report

Shipped everywhere: @property (Properties & Values API)
This is Houdini, and you have been using it since Lesson 4.7. Registering a custom property with a syntax, inheritance behavior, and initial value is the one Houdini idea every engine adopted — because it moved into pure CSS and needed no worklets.
Shipped Chrome-only: the Paint API, and Typed OM in part
Chrome and Edge have shipped CSS.paintWorklet since Chrome 65. Firefox and Safari have not shipped it and show no current intent. Typed OM is complete in Chromium and only partially implemented elsewhere — feature-detect before relying on it.
Stalled: the Layout API and Animation Worklet
The Layout API never left origin trials. Animation Worklet was effectively superseded by scroll-driven animations (Lesson 9.3) — declarative CSS won that race, which is the recurring Houdini lesson: when a shipped CSS primitive can express the design, it beats a worklet every time.

Anatomy of a paint worklet

The Paint API has four moving parts. A worklet file defines a painter class; static inputProperties declares which custom properties it reads (register them with @property so they arrive typed); paint(ctx, size, props) draws with a Canvas-like context every time the element needs repainting; and CSS invokes it anywhere an image is valid:

/* checker.js — runs in the worklet scope, not the page */
class CheckerPainter {
  static get inputProperties() {
    return ['--tint', '--density'];
  }
  paint(ctx, size, props) {
    const density = parseFloat(props.get('--density')) || 8;
    const tint = String(props.get('--tint')).trim();
    const cell = size.width / density;
    for (let y = 0; y * cell < size.height; y++) {
      for (let x = 0; x < density; x++) {
        if ((x + y) % 2 === 0) {
          ctx.fillStyle = tint;
          ctx.fillRect(x * cell, y * cell, cell, cell);
        }
      }
    }
  }
}
registerPaint('checker', CheckerPainter);
// page script: load the module once
if ('paintWorklet' in CSS) {
  CSS.paintWorklet.addModule('/worklets/checker.js');
}
/* page CSS */
@property --density {
  syntax: "<number>";
  inherits: false;
  initial-value: 8;
}

.tile {
  --tint: oklch(70% 0.18 300);
  --density: 8;
  background-image: paint(checker);
  transition: --density 400ms ease;  /* registered → animatable */
}
.tile:hover { --density: 16; }

Because --density is listed in inputProperties and registered via @property, changing or transitioning it automatically re-invokes paint() each frame — the engine treats your painter like any other image source that depends on style.

Typed OM: numbers, not strings

The other Houdini piece worth knowing is the Typed Object Model. el.style traffics in strings — every read parses, every write re-parses, and a typo produces a silently ignored declaration. Typed OM exchanges real value objects:

// String OM: parse → math → stringify → re-parse, every frame
el.style.width = (parseFloat(el.style.width) + 10) + 'px';

// Typed OM: numbers stay numbers
const w = el.attributeStyleMap.get('width');   // CSSUnitValue {value: 120, unit: 'px'}
el.attributeStyleMap.set('width', CSS.px(w.value + 10));

// Invalid values throw at set time instead of failing silently
el.attributeStyleMap.set('width', CSS.deg(45)); // TypeError, immediately

For animation-heavy JavaScript this is both faster (no string round-trips in the hot path — the same concern Lesson 20.11 weighs when choosing CSS vs JS animation) and safer (type errors surface at the call site). It is complete in Chromium and partial elsewhere, so feature-detect: if (el.attributeStyleMap) { … }.

The PE7 verdict: fallback-first, primitives-first

Paint API code never ships without a fallback, and CSS hands you the mechanism for free: an engine that does not recognize paint() treats the declaration as invalid at parse time and keeps the previous one. So declare the boring background first and the painter second. There is a second failure mode people miss: in a supporting engine, paint(checker) parses even if the worklet module never loaded — and an unregistered painter draws nothing. The later declaration still wins the cascade, hiding your gradient. Defend both flanks:

.tile {
  background-color: oklch(28% 0.06 300);          /* 1. always paints   */
  background-image: linear-gradient(135deg,        /* 2. parse-time      */
    oklch(70% 0.18 300), oklch(55% 0.2 260));      /*    fallback        */
  background-image: paint(checker);                /* 3. enhancement     */
}

Better still: apply paint() from a class your script adds only after addModule() resolves (the demo below does exactly this). And before reaching for a worklet at all, ask whether a shipped primitive expresses the design — gradients (Lesson 14.6), masks, or a custom @function (Lesson 10.3) cover most "custom background" briefs with zero JavaScript and universal support.

Browser support

Experimental tier overall. Paint API: Chrome 65+ and Edge only; Firefox and Safari do not ship it and have no announced plans. Typed OM: complete in Chromium, partial in Safari and Firefox — feature-detect attributeStyleMap. @property: production-ready everywhere (Chrome 85+, Firefox 128+, Safari 15.4+ — see Lesson 4.7). Treat paint() as a decorative bonus layer, never as the only rendering of meaningful UI.

Mini-exercise

In a Chromium browser, open the demo and rewrite the worklet to draw diagonal stripes instead of a checkerboard (hint: ctx.rotate() or stepped fillRect offsets), keeping --pe-density as the stripe count. Then open the console and move the tile with Typed OM — $0.attributeStyleMap.set('width', CSS.px(420)) — and compare with the string equivalent. Finally, disable JavaScript in DevTools and reload: confirm the demo degrades to the gradient with the notice visible, proving the fallback chain end to end.
