Lesson 13.21

Integrating @layer with Tailwind, Bootstrap & Third-Party CSS

The single most asked question about @layer in production: how do I use it with my existing framework? Three patterns that permanently solve framework specificity wars.

The problem

You adopt a CSS framework — Tailwind, Bootstrap, a component library. You write custom component styles. Specificity conflicts appear immediately. Your .card component is overridden by Bootstrap's .card. Your custom button color loses to a utility class. You start adding !important, then more !important, then inline styles. The specificity war has begun and there are no winners.

@layer ends this permanently. Layered styles always lose to unlayered styles. Lower layers always lose to higher layers. Specificity within a layer only competes against the same layer. The architecture is deterministic.

Pattern 1: Wrapping Tailwind in layers

/* Layer order declaration — lower = less priority */
@layer vendor, reset, layout, components, utilities;

/* Tailwind's layers wrapped in your architecture */
@import "tailwindcss/base" layer(vendor);
@import "tailwindcss/components" layer(vendor);
@import "tailwindcss/utilities" layer(utilities);

/* Your styles live in higher-priority layers */
@layer reset {
  *, *::before, *::after { box-sizing: border-box; }
}

@layer components {
  .card {
    /* This beats Tailwind's .card automatically —
       components layer > vendor layer */
    padding: var(--space-md);
    background: var(--surface-raised);
    border-radius: var(--radius-md);
  }
}

Tailwind's base and components go in the vendor layer — the lowest priority. Tailwind's utilities go in the utilities layer — the highest priority, which preserves their intended behavior as overrides. Your component styles live in between and beat vendor styles without specificity tricks.

Pattern 2: Wrapping Bootstrap in a layer

@layer vendor, reset, layout, components, utilities;

/* One line: all of Bootstrap in a single layer */
@import url("bootstrap.min.css") layer(vendor);

@layer components {
  /* Your .btn beats Bootstrap's .btn —
     no !important, no specificity hacks */
  .btn {
    background: var(--color-primary);
    color: var(--color-on-primary);
    border: none;
    padding: var(--space-xs) var(--space-md);
    border-radius: var(--radius-sm);
    font-weight: var(--weight-semibold);
  }
}

Wrapping the entire framework in one layer(vendor) import means every Bootstrap selector — no matter how specific — is lower priority than your components layer. A single-class selector in components beats a three-class selector in vendor. Specificity only matters within the same layer.

Pattern 3: The escape hatch

@layer vendor, reset, layout, components, utilities;

@import url("framework.css") layer(vendor);

@layer components {
  .modal { /* normal component styles */ }
}

/* Unlayered styles beat ALL layers — emergency fix */
.modal-override {
  z-index: 9999;
  position: fixed;
}

Styles that are not inside any @layer block have higher priority than all layered styles, regardless of specificity. This is the escape hatch for emergency production fixes — a surgical override that bypasses the entire layer stack. Use it intentionally and rarely.

The PE7 integration strategy

/* Full PE7 layer stack with vendor integration */
@layer vendor, reset, tokens, layout, components, utilities;

/* Third-party CSS always goes in vendor */
@import url("bootstrap.min.css") layer(vendor);
@import url("some-carousel.css") layer(vendor);

/* Your architecture sits above */
@layer tokens   { :root { --color-primary: oklch(55% 0.22 275); } }
@layer reset    { *, *::before, *::after { box-sizing: border-box; } }
@layer layout   { .stack > * + * { margin-block-start: var(--space-md); } }
@layer components { .card { /* your card */ } }
@layer utilities { .visually-hidden { /* a11y utility */ } }

Vendor CSS goes in a vendor layer below reset. Your architecture layers sit above it. Framework specificity wars are permanently solved because the layer order is explicit, deterministic, and documented in a single line at the top of your stylesheet.

What about frameworks that use @layer internally?

Some modern frameworks ship their own @layer declarations. When you wrap them in layer(vendor), their internal layers become nested: vendor.base, vendor.components, etc. Nested layers are always lower priority than the parent layer's siblings. This works correctly — the framework's internal layer order is preserved within the vendor layer, and the vendor layer as a whole is still lower than your layers.

Browser support

@layer is supported in Chrome 99+, Firefox 97+, Safari 15.4+. The @import ... layer() syntax is supported in the same versions. Production-ready.

Try it yourself

Mini-exercise

Add an unlayered style rule that overrides the .btn-primary background to a vivid red: oklch(60% 0.24 25). Place it outside any @layer block. Observe how it beats both the vendor and component layers without !important. This is the escape hatch — useful for emergency production fixes, but use it sparingly. If your codebase has more than a handful of unlayered overrides, it is time to add a new layer instead.
