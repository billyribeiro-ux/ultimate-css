Highlight Pseudo-Elements & the Custom Highlight API

The pseudo-elements in Lesson 28.6 generate boxes — ::before and ::after participate in layout. Highlight pseudo-elements are a different mechanism entirely: they paint styling over arbitrary ranges of already-laid-out text, with no extra DOM and no layout impact. That model powers ::selection, deep-link highlighting, spellcheck squiggles — and, through the Custom Highlight API, your own named ranges.

A different kind of pseudo-element

A highlight pseudo-element represents a set of text ranges, not a box. The browser lays out the text exactly as if no highlight existed, then paints the highlight's styling over the affected glyphs during the paint phase. This is the root cause of every rule in this lesson: because no box exists and layout is already done, only properties that can be applied at paint time are honored. The family: ::selection, ::target-text, ::spelling-error, ::grammar-error, and the parameterized ::highlight(name).

::selection done right

Only a small set of properties applies — the spec allows roughly: color, background-color, text-decoration (and its longhands), text-shadow, plus text-emphasis-color and stroke/fill for SVG text. font-size, padding, display — anything that would change geometry — is ignored, because honoring it would force a relayout every time the user dragged a selection.

::selection {
  background-color: oklch(45% 0.18 275);
  color: oklch(98% 0.01 275);
}
/* Set BOTH color and background-color together. Styling only one
   risks an unreadable combination against the UA default of the
   other — the classic white-on-pale-blue bug. */

Accessibility is non-negotiable here: selection is a functional state, not decoration. Keep at least 4.5:1 contrast between your selection foreground and background, and never set background-color: transparent as a "minimal" aesthetic — users lose the only visual confirmation of what they are about to copy.

::target-text and scroll-to-text fragments

URLs can deep-link to text, not just IDs: a fragment of the form #:~:text=some%20phrase makes the browser scroll to and highlight the first match. ::target-text styles that highlight, replacing the UA default (typically purple-on-yellow) with something on-brand. Production — text fragments and ::target-text are supported in all three engines (Chrome 89+, Safari 18.2+, Firefox 131+).

/* https://example.com/article#:~:text=key%20finding */
::target-text {
  background-color: oklch(85% 0.17 95);
  color: oklch(20% 0.02 95);
}

The same painted-range property restrictions apply. This is worth styling in any documentation or content product: search engines, LLM citations, and "copy link to highlight" features all generate text-fragment URLs into your pages whether you style them or not.

::spelling-error and ::grammar-error

These style the ranges the browser's checker flags in editable text. The honored property set is the same, plus the two purpose-built decoration values text-decoration-line: spelling-error and grammar-error, which reproduce the native squiggle so you can recolor without redrawing it. Progressive — shipped in Chromium and Firefox, not yet in Safari; unsupported engines simply keep their native squiggles, so no @supports gate is needed.

::spelling-error {
  text-decoration-line: spelling-error;
  text-decoration-color: oklch(60% 0.24 25);
}
::grammar-error {
  text-decoration-line: grammar-error;
  text-decoration-color: oklch(55% 0.15 230);
}

The Custom Highlight API

The previous pseudos style ranges the browser chooses. The Custom Highlight API lets you register your own: build Range objects in JavaScript, group them into a Highlight, and register it in the CSS.highlights map under a name. CSS then paints it via ::highlight(name) — the JS defines where, the CSS defines how. Production as of 2026: Chrome 105+, Safari 17.2+, Firefox 140+.

// JS — define the ranges
const range = new Range();
range.setStart(textNode, 10);
range.setEnd(textNode, 24);

const hits = new Highlight(range /*, ...moreRanges */);
CSS.highlights.set('search-hits', hits);

/* CSS — paint them */
::highlight(search-hits) {
  background-color: oklch(88% 0.16 95);
  color: oklch(22% 0.03 95);
}

Feature-detect with 'highlights' in CSS on the JS side. There is nothing to gate in the CSS — an unmatched ::highlight() rule is inert.

The highlight inheritance model

Highlight pseudos do not inherit from their originating element. They inherit through a parallel highlight chain: an element's ::selection inherits from its parent's ::selection, and so on up to the root. Two practical consequences. First, a root-level ::selection theme genuinely cascades to all text — the old advice to write *::selection is obsolete (and worse, since per-element universal rules block chain inheritance of later overrides). Second, custom properties used inside highlight styles resolve against the originating element, so token-driven highlight theming works exactly as you would expect.

:root::selection { background-color: var(--selection-bg); }
/* every element's ::selection inherits this via the highlight
   chain — no universal selector needed */

.danger-zone { --selection-bg: oklch(50% 0.2 25); }
/* custom properties resolve against the element — local retheme */

What custom highlights are for

The defining win is styling text ranges without mutating the DOM. The traditional find-in-page implementation wraps every hit in a <mark> or <span> — which splits text nodes, invalidates layout, breaks user selections and caret position, fights frameworks that own the DOM, and must be carefully unwrapped afterwards. Registering a Highlight does none of that: zero DOM mutation, zero layout cost, paint-only updates. Production patterns:

  • Search-hit highlighting in long documents — thousands of ranges paint cheaply where thousands of injected spans would jank.
  • Collaborative presence — each remote user's cursor/selection becomes one named highlight (::highlight(user-ada)), updated on every websocket message without touching the document.
  • Editor hints — syntax emphasis or lint underlines painted over a contenteditable surface whose DOM must stay clean.

Overlapping highlights: priority and stacking

Ranges overlap, so the spec defines a deterministic paint order. Custom highlights stack in registration order in the CSS.highlights map (later paints over earlier) unless you set the priority property on a Highlight — higher numbers paint on top. Native highlights have fixed positions in the stack: spelling and grammar errors sit above custom highlights, and ::selection paints above everything, which is why selecting across your search hits always remains visible. For each property, the topmost highlight that sets it wins; properties it does not set show through from highlights below. Selector specificity behaves normally otherwise — ::highlight(x) contributes like any pseudo-element, and conflicts between rules for the same highlight resolve by the ordinary cascade from Lesson 28.10's world: keep these selectors flat and let layers order them.

const spell = new Highlight(...ranges);
spell.priority = 2;            // paint above 'search-hits'
CSS.highlights.set('lint', spell);

Mini-exercise

Build a dependency-free find-in-page. (1) Add a text input and a long article to a page; on input, walk the article's text nodes with a TreeWalker, build a Range for each match, and register them as CSS.highlights.set('find', new Highlight(...ranges)). (2) Style ::highlight(find) with a background/foreground pair that passes 4.5:1. (3) Add a second highlight named find-current for the active match with priority = 1 and confirm it paints above the others. (4) Open the DOM inspector while searching and verify the document never changes — then select across the hits and observe ::selection painting above both, exactly as the native stacking order specifies.
