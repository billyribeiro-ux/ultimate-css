Lesson 11.1

No-JS Philosophy: Where the Line Sits

The no-JS argument is not about purity. It is about picking the most durable implementation for each piece of UI. This lesson lays out the three-part test we use to decide, and draws the line precisely between what CSS now owns and where JavaScript is still essential.

The three-part test

For any UI pattern, ask these three questions in order. If the answer to all three is yes, prefer the no-JS implementation.

  1. Is it more accessible? Native HTML and CSS give you keyboard handling, ARIA roles, focus trapping, and screen reader semantics for free — implementations custom-built in JavaScript need to reimplement every one of those and will get some of them wrong.
  2. Is it more performant? Zero-JS patterns ship zero JS. They boot instantly, work with JavaScript disabled, and eliminate a whole class of hydration bugs.
  3. Is it more maintainable? An HTML primitive has a stable spec. A JavaScript reimplementation is five packages deep in a dependency tree that expires on a 6-month cycle.

Where JavaScript is still essential

This module is not a trick — there are categories where JavaScript is still the right answer, and it is important to name them:

  • Application state. A shopping cart, a form that builds up over multiple pages, a real-time collaborative editor. CSS cannot hold application state.
  • Data fetching and mutation. Talking to an API, optimistic updates, cache invalidation.
  • Dynamic ARIA announcements. aria-live regions. CSS can change what is visible; only JavaScript can change what a screen reader reads out at a specific moment.
  • Complex timeline animation. Overlapping beats with interruption recovery (Lesson 9.8).
  • Physics, gestures, inertia. Drag-with-momentum, custom pinch-zoom.

Where CSS now wins

This is the module's scope:

  • Accordions (<details>/<summary>)
  • Tabs (:target)
  • Modals and popovers (popover attribute)
  • Tables of contents with scrollspy (:target-current)
  • Carousels (scroll-snap + scroll-marker-group)
  • Dropdowns (:has() + <details>)

The honest trade-offs

Every no-JS pattern has a cost. Anchor-based tabs put state in the URL — great for deep linking, awkward for multi-tab pages. <details> animation required @starting-style to become smooth. Popovers require a modern browser. Each lesson that follows names its trade-off explicitly. No sales pitches.

Try it yourself

Mini-exercise

Open a UI component in your current project — any widget you built or reached for a library for. Apply the three-part test. Is the JavaScript implementation actually buying you more accessibility, performance, or maintainability than the native primitive? Write down the honest answer.
