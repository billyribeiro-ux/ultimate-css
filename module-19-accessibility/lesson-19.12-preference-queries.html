Lesson 19.12 · Inclusive Design

Every User Preference: The Complete Media Query Set

This module has already honored three user signals: prefers-reduced-motion (19.3), prefers-color-scheme (19.7), and forced-colors (19.6). But the platform exposes far more — contrast, transparency, data, inversion, refresh rate, scripting, even how the app was launched. This lesson completes the set, then shows the PE7 move: answer all of them in one place, at the token level.

The principle: no user signal ignored

Every one of these media features exists because a user, somewhere in their OS settings, told the platform something about their body, their hardware, or their budget. Ignoring the signal is not neutral — it actively overrides a stated need. The good news: each query costs a few lines of CSS, and because they are media queries, unsupported ones are simply skipped. There is no fallback work to do; the un-matched state is the fallback.

prefers-contrast: more / less / custom

Production-ready (Chrome 96+, Firefox 101+, Safari 14.1+). At more, strengthen the cues that low-vision users rely on: thicker borders, darker text, no "subtle gray on white" anywhere. At less (rare, but real — light sensitivity, migraine triggers), soften harsh pure-black-on-white. custom fires when the user runs a forced palette — it matches alongside forced-colors: active (Lesson 19.6), so treat it as "the OS owns colors now, defer to system keywords":

@media (prefers-contrast: more) {
  :root {
    --border-w: 2px;
    --ink: oklch(12% 0.02 270);      /* was 35% */
    --ink-muted: oklch(25% 0.02 270); /* "muted" must still pass AAA */
  }
}

@media (prefers-contrast: custom) {
  /* forced palette active — system colors take over (see 19.6) */
  :root { --ink: CanvasText; --surface: Canvas; }
}

prefers-reduced-transparency

Progressive (Chrome 118+, others planned). Every frosted-glass surface this course built — Apple's nav (14.3), Fluent acrylic (14.22), animated glassmorphism (15.10) — assumes the user can read text over a blurred, shifting backdrop. Vestibular and low-vision users often cannot. The query asks for solid surfaces, and the fix is two token flips:

@media (prefers-reduced-transparency: reduce) {
  :root {
    --surface-glass: oklch(98% 0.01 270);  /* was / 0.6 alpha */
    --surface-blur: 0px;                   /* backdrop-filter: blur(var(--surface-blur)) */
  }
}

prefers-reduced-data

Experimental (behind flags in Chromium; no other engine yet). The user is saying "bytes cost me money." Honor it by skipping decorative downloads: background images become gradients, webfonts (Lesson 20.6) yield to system fonts. Because it is a media query, the browser never even requests assets referenced only inside a non-matching block:

.hero { background-image: var(--hero-image, none); }

@media (prefers-reduced-data: no-preference) {
  :root { --hero-image: image-set("hero.avif" type("image/avif")); }
  /* @font-face loading can live here too */
}

Note the inversion: gate the expensive path behind no-preference so flag-less browsers still load it, while opted-in users skip it the moment support lands.

inverted-colors

Progressive (Safari, plus recent Chrome). OS-level color inversion is a long-standing low-vision aid — but it turns photographs and video into negatives. Faces become ghoulish; charts lie. The defensive rule is one line — re-invert continuous-tone media so it survives the round trip:

@media (inverted-colors: inverted) {
  img, video, .photo { filter: invert(1); }
}

update and scripting: the environment queries

update reports how fast the display can repaint: fast (typical screens), slow (e-ink, some embedded displays), none (print). On slow/none, animation is at best wasted and at worst unreadable smearing — and color-only cues fade on grayscale e-ink, so prefer structural cues like underlines:

@media (update: slow), (update: none) {
  * { animation: none !important; transition: none !important; }
  a { text-decoration: underline; } /* never color-only on e-ink */
}

scripting: enabled / initial-only / none styles no-JS states declaratively — the modern replacement for .no-js class flipping, and a direct continuation of Lesson 11.1's philosophy:

@media (scripting: none) {
  .needs-js { display: none; }
  .static-fallback { display: block; }
}

display-mode and input capabilities

display-mode reports how the app was launched. This very course is an installable PWA — when it runs standalone, there is no browser chrome, so "open in app" banners are redundant and safe-area padding matters:

@media (display-mode: standalone) {
  .install-banner { display: none; }
  .site-header { padding-block-start: env(safe-area-inset-top); }
}

And recall the input queries from Lesson 19.8: pointer/hover describe the primary input, any-pointer/any-hover describe all of them. The input-adaptive density pattern — bigger touch targets when the primary pointer is coarse, hover-revealed affordances only when hover truly exists — is the same preference-respecting instinct applied to hardware.

The preference cascade: answer everything at the token level

The PE7 synthesis: components must never branch on preferences. If every card, nav, and button carries its own stack of @media blocks, you will miss one — guaranteed. Instead, each preference flips tokens in one auditable place, and components consume tokens as usual (Lesson 4.8's aliasing made this cheap):

:root {
  --border-w: 1px;
  --ink: oklch(35% 0.02 270);
  --surface-glass: oklch(98% 0.01 270 / 0.6);
  --surface-blur: 12px;
  --hero-image: none;
  --motion: 1;  /* multiply durations: calc(300ms * var(--motion)) */
}

@media (prefers-contrast: more)               { :root { --border-w: 2px; --ink: oklch(12% 0.02 270); } }
@media (prefers-reduced-transparency: reduce) { :root { --surface-glass: oklch(98% 0.01 270); --surface-blur: 0px; } }
@media (prefers-reduced-motion: reduce)       { :root { --motion: 0; } }
@media (update: slow), (update: none)         { :root { --motion: 0; } }
@media (prefers-reduced-data: no-preference)  { :root { --hero-image: url("hero.avif"); } }

/* Components never branch: */
.card { border: var(--border-w) solid currentColor; color: var(--ink); }

One file, every signal, zero per-component audits. New preference query ships? You add one line here, and the whole system responds.

Mini-exercise

Audit a project you have built in this course (the glassmorphism card from 15.10 is a good candidate) against the complete set: does it respond to prefers-contrast: more, prefers-reduced-transparency, update: slow, and inverted-colors?
