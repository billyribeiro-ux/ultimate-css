The CSS Accessibility Audit Checklist

A comprehensive, actionable checklist for auditing the CSS accessibility of any web page. Each item maps to a WCAG success criterion. Run through this list before shipping, and you will catch the vast majority of CSS-related accessibility failures.

The checklist

1. Focus indicators (WCAG 2.4.7, 2.4.11)

  • Every interactive element has a visible focus indicator when navigated via keyboard.
  • Custom focus rings use :focus-visible (not :focus alone) to avoid showing rings on mouse click.
  • Focus ring has at least 3:1 contrast against the adjacent background.
  • Focus ring is at least 2px thick with appropriate outline-offset.
  • Skip link exists and becomes visible on focus.

2. Color contrast (WCAG 1.4.3, 1.4.6)

  • Normal text: 4.5:1 minimum against its background.
  • Large text (18pt+, or 14pt bold): 3:1 minimum.
  • UI components and graphical objects: 3:1 minimum.
  • Placeholder text meets 4.5:1 (not just the default browser gray).
  • Contrast verified in BOTH light and dark mode.

3. Reduced motion (WCAG 2.3.3)

  • @media (prefers-reduced-motion: reduce) is implemented.
  • Non-essential animations are disabled or replaced with opacity-only transitions.
  • No auto-playing animations that cannot be paused.
  • Parallax effects are disabled in reduced-motion mode.

4. Content reflow (WCAG 1.4.10)

  • At 320px viewport width, no horizontal scrollbar appears.
  • At 200% browser zoom, all content remains accessible without horizontal scrolling.
  • Text containers use max-inline-size not fixed pixel widths.
  • Grid/flex layouts use auto-fit or flex-wrap for natural reflow.

5. Text sizing (WCAG 1.4.4)

  • Font sizes use rem or em, not px.
  • Text can be resized to 200% without loss of content or functionality.
  • Line heights are unitless (e.g., 1.5 not 24px).
  • clamp() patterns include a rem minimum.

6. Forced colors (WCAG 1.4.11)

  • Tested in Windows High Contrast Mode (or emulated via DevTools).
  • Elements that rely on background for boundaries have border fallbacks in @media (forced-colors: active).
  • Buttons have visible borders in forced-colors mode.
  • Custom controls use system colors where appropriate.

7. Touch targets (WCAG 2.5.8)

  • All interactive elements are at least 44x44px (recommended) or 24x24px (minimum AA).
  • Adjacent targets have at least 8px gap between them.
  • Small visual elements use ::after stretch pattern for larger hit areas.
  • min-block-size used instead of fixed height.

8. Screen reader content

  • No content hidden from screen readers unintentionally (check for display: none on needed content).
  • .sr-only class available for visually-hidden-but-accessible text.
  • Decorative pseudo-element content does not confuse screen readers.
  • Icon-only buttons have accessible labels (via .sr-only or aria-label).

9. ARIA states styled

  • Interactive components use ARIA attributes as CSS selectors (not separate classes).
  • [aria-expanded] drives open/closed visual states.
  • [aria-current="page"] styles the active navigation item.
  • [aria-invalid="true"] drives error styling on form fields.

10. Logical properties and RTL

  • Layout uses inline-start/end and block-start/end instead of left/right/top/bottom where appropriate.
  • Page tested in RTL mode (dir="rtl" on html) to verify correct mirroring.
  • Icons and directional elements flip correctly with writing direction.

How to run the audit

Step 1: Keyboard walkthrough

Put your mouse away. Starting from the browser address bar, press Tab to move through every interactive element on the page. Verify:

  • You can reach every button, link, and form control.
  • Focus order is logical (follows visual reading order).
  • Each focused element has a clearly visible indicator.
  • Modal dialogs trap focus — Tab does not escape to the background.
  • Escape key closes modals and returns focus to the trigger.
  • Skip link appears on first Tab press and jumps past navigation.

Step 2: Browser DevTools Accessibility Panel

Chrome, Firefox, and Edge all have built-in accessibility inspectors. Open DevTools, go to the Accessibility tab (Chrome) or Accessibility Properties panel (Firefox). This shows the computed accessible name, role, and state for every element. Walk through the accessibility tree and verify:

  • Every interactive element has an accessible name.
  • ARIA states match the visual state (expanded matches open, etc.).
  • No elements are accidentally removed from the tree by display: none or visibility: hidden.
  • Decorative elements are properly marked with aria-hidden="true".

Step 3: Automated scanning

Chrome Lighthouse: Run an accessibility audit from the DevTools Audits/Lighthouse panel. It catches many contrast failures, missing labels, and focus issues. axe DevTools extension: More thorough automated testing with clear fix suggestions. WAVE browser extension: Visual overlay showing errors directly on the page.

Note: automated tools catch only ~30-50% of accessibility issues. They are a starting point, not a complete audit.

Step 4: Visual checks

  • Zoom test: Set browser zoom to 200%. Verify no horizontal scrollbar appears and all content is readable. Repeat at 400%.
  • Reduced motion: In DevTools Rendering panel, emulate prefers-reduced-motion: reduce. Verify animations are suppressed or simplified.
  • Forced colors: In DevTools Rendering panel, emulate forced-colors: active. Verify all elements remain visible with proper borders.
  • Dark mode: Toggle to dark mode. Re-check all contrast ratios — colors that pass in light mode may fail in dark mode.
  • Viewport resize: Drag the browser window to 320px width. Verify single-column reflow without overflow.

Step 5: Screen reader testing

Use VoiceOver (macOS, Cmd+F5), NVDA (Windows, free), or Orca (Linux). Navigate the page using screen reader commands (not Tab alone). Verify:

  • Headings create a logical outline (navigate by heading shortcuts).
  • Landmark regions are announced (nav, main, banner, contentinfo).
  • Form fields announce their labels and error states.
  • Dynamic content changes are announced (live regions, aria-live).
  • Decorative content is not announced.

Step 6: Touch target verification

Using DevTools, inspect every button and link. Check computed dimensions — the clickable area (including padding) should be at least 44x44px. For elements using the ::after stretch pattern, verify the pseudo-element extends the hit area sufficiently. On mobile devices or in responsive mode, attempt to tap each target without accidental mis-taps.

Common failure patterns

These are the CSS-related accessibility failures encountered most frequently in production:

  • outline: none without replacement: Removes focus visibility entirely. Fix: replace with :focus-visible custom styles.
  • Low contrast placeholder text: Default browser gray often fails 4.5:1. Fix: style ::placeholder with sufficient contrast.
  • Fixed-width containers: width: 800px causes horizontal scroll at zoom. Fix: use max-inline-size with fluid values.
  • Hover-only interactions: Dropdown menus that only open on hover are inaccessible to keyboard and touch users. Fix: use :focus-within alongside :hover.
  • Color as the only indicator: Red text for errors without any other visual cue (border, icon) fails for color-blind users. Fix: add border changes and text labels.
  • Tiny close buttons: Modal close buttons at 16x16px are impossible to tap on mobile. Fix: minimum 44x44px with padding or ::after stretch.
  • overflow: hidden on text containers: Clips content when users increase font size. Fix: use overflow: visible or overflow-wrap: break-word.
  • Animations without reduced-motion guard: Every @keyframes and transition should have a reduced-motion fallback. Fix: use the PE7 global override pattern.
  • display:none on content meant for screen readers: Removes from the accessibility tree. Fix: use .sr-only pattern instead.
  • Custom scrollbars that remove native focus indicators: Styling scrollbars can interfere with keyboard focus visibility in scroll containers. Fix: test keyboard scroll after customization.

Audit frequency

Accessibility audits should happen at three points in the development cycle:

  • Design review: Check color contrast, touch target sizes, and motion plans before any code is written. Catching issues here costs minutes, not hours.
  • Pull request: A 5-minute keyboard walkthrough of changed components. Run axe-core or Lighthouse on the affected pages. Check the CSS diff for outline: none, fixed pixel widths, or missing reduced-motion guards.
  • Pre-release: Full manual audit covering all 10 checklist sections. Screen reader testing on at least one platform. Zoom testing at 200% and 400%. Forced-colors and reduced-motion emulation. This is the gatekeeper before users encounter the code.

The cost of retrofitting

Fixing accessibility in an existing codebase is 5-10x more expensive than building it in from the start. Every outline: none that shipped without a replacement now requires finding every affected element and adding custom focus styles. Every pixel-based layout that fails reflow requires a significant refactor to logical properties and fluid values. Build accessibility into your CSS architecture from day one — it is a structural decision, not a cosmetic one.

CSS properties to grep for in audits

When auditing an existing codebase, search for these patterns that frequently indicate accessibility issues:

/* Likely problems — search for these */
outline: none       /* focus removal without replacement */
outline: 0          /* same issue */
:focus { ... }      /* without :focus-visible variant */
font-size: ??px     /* pixel font sizes */
width: ???px        /* fixed widths on text containers */
height: ???px       /* fixed heights that clip at zoom */
overflow: hidden    /* may clip zoomed content */
user-select: none   /* prevents text copying */
pointer-events: none /* without aria-disabled */

/* Good patterns to look for */
:focus-visible      /* keyboard-only focus */
prefers-reduced-motion  /* motion respect */
forced-colors       /* high contrast support */
min-block-size      /* flexible sizing */
clamp(             /* fluid typography */
.sr-only           /* screen reader utility */

Integrating with CI/CD

Automated accessibility testing in your CI pipeline catches regressions before they reach production:

  • axe-core + Playwright/Cypress: Run axe on every page in your end-to-end test suite. Fail the build on any new violations.
  • Lighthouse CI: Set accessibility score thresholds. Alert when the score drops below 95.
  • CSS linting: Configure stylelint rules to flag outline: none without an adjacent :focus-visible rule, or font-size in px.
  • Visual regression: Capture screenshots in forced-colors mode and reduced-motion mode. Diff against baselines to catch visual regressions that affect accessibility.

Using this checklist

Print this page or save it as a reference. Before shipping any component, page, or design system update, run through each section. The items are ordered by frequency of failure — focus and contrast issues are the most common, followed by reflow and touch target problems. Catching these in development is 10x cheaper than fixing them after deployment.

For teams: incorporate this checklist into your pull request template. A quick 5-minute keyboard walkthrough before merge catches the majority of regressions. Pair it with automated CI checks (axe-core in your test suite) for comprehensive coverage.
