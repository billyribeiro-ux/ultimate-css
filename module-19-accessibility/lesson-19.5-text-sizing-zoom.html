Lesson 19.5 · Inclusive Design

Text Sizing, Zoom & Reflow

Many users zoom to 200% or even 400%. WCAG requires that content remains functional without horizontal scrolling at 320px equivalent width. The key: use rem, logical properties, and fluid type — never fixed pixel widths for text containers.

Why rem, not px, for font-size

When you set font-size: 16px, the text cannot scale with the user's browser font-size preference. A user who sets their default to 20px gets no benefit. Using font-size: 1rem respects their choice. This is a WCAG 1.4.4 requirement: text must be resizable up to 200% without loss of content or functionality.

WCAG 1.4.10 — Reflow

At 320px viewport width (equivalent to 1280px at 400% zoom), content must reflow into a single column with no horizontal scrolling. Exceptions: data tables, toolbars, and content where two-dimensional layout is essential for meaning.

The practical test: set your viewport to 320px wide (DevTools device toolbar) and verify nothing overflows or requires side-scrolling.

Logical properties enable correct reflow

margin-inline, padding-block, inline-size, block-size — these adapt to writing direction. For reflow, max-inline-size is safer than max-width because it adjusts for vertical writing modes. More importantly, thinking in terms of inline/block naturally produces layouts that stack gracefully.

The clamp() pattern for fluid type

h1 {
  font-size: clamp(1.5rem, 1rem + 2vw, 3rem);
}
body {
  font-size: clamp(1rem, 0.9rem + 0.5vw, 1.25rem);
}

The minimum value uses rem, so it scales with user preferences. The preferred value mixes rem and vw for fluidity. The maximum caps the growth. This pattern passes WCAG because the rem base ensures user scaling still works.

Testing at 200% and 400%

Browser zoom at 200% doubles everything — if your layout uses flexbox with flex-wrap: wrap or grid with auto-fit, it naturally reflows. Fixed-width sidebars, hardcoded pixel breakpoints, and overflow: hidden on text containers are the usual failure points.
