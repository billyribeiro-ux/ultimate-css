Lesson 19.9 · Inclusive Design

content-visibility & Accessibility Pitfalls

content-visibility: auto is a powerful performance optimization — it skips rendering of off-screen content. But it also hides that content from browser find-in-page (Ctrl+F) and can confuse screen readers. Here is when to use it and when to avoid it.

What content-visibility: auto does

When an element with content-visibility: auto is off-screen, the browser skips its layout, paint, and style calculations entirely. This can dramatically improve initial render time for long pages. When the element scrolls into view, it renders normally.

The find-in-page problem

Browser find-in-page (Ctrl+F / Cmd+F) may not search text inside elements with content-visibility: auto that are currently off-screen. This means users searching for content will not find it. Chromium browsers have improved this, but the behavior is still inconsistent across engines.

The contain-intrinsic-size requirement

Without contain-intrinsic-size, the off-screen element has 0 height, causing the scrollbar to jump as content renders. Always pair them:

.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 500px;
}

The auto keyword remembers the last rendered size, preventing layout shifts on re-scroll.

When NOT to use it

  • Main content area: If the primary text of your page uses content-visibility, search engines and find-in-page may miss it.
  • Critical text: Legal notices, terms, accessibility statements — content users actively search for.
  • Above-the-fold content: Already visible on load, so there is no benefit and potential CLS risk.
  • Landmark regions: Screen readers navigate by landmarks; hiding them disrupts navigation.

Safe patterns

Use content-visibility: auto on below-fold sections that are supplementary: image galleries, comments sections, footer widgets, related-articles grids. The content is still accessible — it just does not render until the user scrolls to it.

The contentvisibilityautostatechange event

This JavaScript event fires when the element transitions between visible and hidden states. For JS-dependent content (lazy-loaded images, interactive widgets), listen for this event to initialize when the section becomes visible:

section.addEventListener('contentvisibilityautostatechange', (e) => {
  if (e.skipped === false) {
    // Element is now visible — initialize lazy content
    loadImages(section);
  }
});

content-visibility: hidden vs display: none

content-visibility: hidden (not auto) behaves like display: none for rendering — the element is never painted and is removed from the accessibility tree. The difference: the browser preserves the element's render state, making re-showing it cheaper than toggling display: none. Use it for off-screen tabs or panels that will be shown later, when you want instant reveal without re-layout cost.

Measuring the performance gain

Use Chrome DevTools Performance panel to measure. Record a page load with and without content-visibility: auto on below-fold sections. Look at the "Rendering" time in the summary. For long pages with 20+ sections, you can see 50-80% reduction in initial render time. But always weigh this against the accessibility trade-offs — a faster page that users cannot search is not a net improvement.

The decision framework

  • Is this content below the fold? If no, do not use content-visibility.
  • Would a user likely Ctrl+F for this content? If yes, do not use content-visibility.
  • Is this a landmark region? If yes, do not use content-visibility.
  • Is this supplementary content (comments, galleries, footers)? Safe to use.
  • Does the section contain interactive elements that need to be in the tab order? Test carefully — some browsers skip these when hidden.
