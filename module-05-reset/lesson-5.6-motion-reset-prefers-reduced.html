Lesson 5.6

Motion Reset & prefers-reduced-motion

Users who request reduced motion are telling you — through an operating system preference — that fast transitions cause them nausea or vertigo. Respecting that request is not a nice-to-have. It is the single accessibility rule most deserving of an !important in the reset layer.

The one place !important belongs

The rest of this course is about avoiding !important. Motion reduction is the exception. When a user sets the OS-level reduced-motion flag, they have told the browser that arbitrary component authors — including third-party libraries — must not animate. Any layer in the cascade could have added a transition; the reset has to shut them all down regardless of specificity.

@media (prefers-reduced-motion: reduce) {
  :where(*, *::before, *::after) {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}

Why 0.01ms and not zero?

Setting animation duration to exactly zero skips the animation entirely, including any animationend events. Component code that waits for those events — for example, a modal that dismounts after its exit animation finishes — would hang forever. 0.01ms runs the animation for a single frame, fires the event, and looks instantaneous to the user.

scroll-behavior

Smooth scrolling is also motion. If a user asks for reduced motion, anchor links and scrollIntoView calls should jump instantly rather than animating. scroll-behavior: auto is the instant form; smooth is the animated form. The reset forces instant under reduced-motion.

The :where() exception — still zero specificity

The selector is :where(*, *::before, *::after). :where() keeps the specificity at zero; the !important is what guarantees the rule wins regardless of layer order. This is the only time the two are combined in the PE7 architecture, and it is deliberately restricted to motion properties.

What we do not disable

We do not disable all animation — some animations encode state, like a spinner showing that a request is in flight. The reset shortens their duration to near-zero so the visual flash still communicates state, but never exceeds one frame. Components that need a truly motionless alternative should use a @media (prefers-reduced-motion: reduce) block of their own and swap the visual to a static indicator.

Try it yourself

Mini-exercise

On macOS: System Settings → Accessibility → Display → Reduce motion. On Windows: Settings → Accessibility → Visual effects → Animation effects off. Toggle the setting, re-run the editor, and confirm the box stops sliding. Then write down one place in your last project where you used a transition that would have been disruptive under reduced motion. That is the rule you would have forgotten without a reset-level enforcement.
