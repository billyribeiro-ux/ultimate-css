Lesson 9.7

View Transitions

A view transition is a snapshot-based morph between two DOM states. You tell the browser "I'm about to change the DOM" and it automatically animates the difference — position, size, opacity, color — between old and new. This is how native apps have felt for twenty years. The web finally has it.

The mental model

Without view transitions, changing the DOM is discontinuous — one frame it's state A, the next it's state B. With view transitions, the browser captures a bitmap of state A, applies the DOM change, captures state B, and then cross-fades between them on the compositor. You only write the animation rules for the transition itself.

The two halves

JavaScript kicks it off — one function call:

document.startViewTransition(() => {
  // Make any DOM changes here.
  list.classList.toggle("grid");
});

CSS defines the animation via two pseudo-elements:

::view-transition-old(root),
::view-transition-new(root) {
  animation-duration: 400ms;
  animation-timing-function: var(--ease-out);
}

Named transitions for morphing elements

Give an element a view-transition-name and the browser will morph it from its old position to its new position, across the DOM change:

.hero-image { view-transition-name: hero; }
::view-transition-group(hero) { animation-duration: 500ms; }

This is how you get the "card in a list expands into a full-screen detail view" feeling without writing a single line of animation code.

Same-document vs cross-document

Same-document view transitions (DOM changes within one page) are in Chrome, Safari, and Firefox. Cross-document (between navigations) is Chrome-only as of early 2026 but rapidly landing. This lesson focuses on same-document — production-ready now.

Mini-exercise

Add a second box with its own view-transition-name. Move it in the DOM inside the startViewTransition callback — from one container to another. The browser will morph it between parents automatically, which is the "shared element transition" pattern that used to require a choreography library.
