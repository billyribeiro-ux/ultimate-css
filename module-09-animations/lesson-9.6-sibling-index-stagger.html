Lesson 9.6

Progressive enhancement

sibling-index() Staggered Motion

Staggered animations — cards fading in one after the other — used to require hand-written :nth-child(N) rules for every index. sibling-index() and sibling-count() give CSS arithmetic access to the DOM's own ordering, making stagger a one-liner.

The old way

.card:nth-child(1) { animation-delay: 0ms; }
.card:nth-child(2) { animation-delay: 60ms; }
.card:nth-child(3) { animation-delay: 120ms; }
/* ...and so on, forever */

This works, but it is a maintenance trap. Add a card and you have to add a rule. Remove one and you have an orphan. The arithmetic is in the CSS but hidden inside hand-computed numbers.

The new way

.card {
  animation: fade-up 400ms ease-out both;
  animation-delay: calc((sibling-index() - 1) * 60ms);
}

One rule. Works for 3 cards or 300. Add or remove cards freely. The arithmetic lives where it belongs — next to the property that consumes it.

sibling-count() for dynamic sizing

sibling-count() returns the total number of siblings. Combine with sibling-index() to express fractions:

.tick {
  --t: calc(sibling-index() / sibling-count());
  background: oklch(70% 0.15 calc(var(--t) * 360));
}

Every tick gets a hue proportional to its position — a full rainbow, auto-distributed, regardless of how many ticks exist.

Browser support

Chrome 139+, Edge 139+. Safari and Firefox not yet. Wrap in @supports (animation-delay: calc(sibling-index() * 1ms)). Fallback: omit the stagger — all cards animate simultaneously, which is still a valid design choice.

Mini-exercise

Add or remove <li> elements in the HTML pane. Confirm the stagger re-computes automatically and the hue stays evenly distributed no matter how many items exist. This is the value of arithmetic-over-indices — your design scales with your data.
