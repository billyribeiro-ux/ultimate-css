Lesson 3.1

Why Architecture Matters

The @layer feature gives you buckets. Architecture is the decision about which buckets exist and what goes in each one. Without that decision, layers just become a new place to hide the old mess.

The 500-line to 5,000-line cliff

Every CSS codebase is pleasant at 500 lines. You can hold the whole thing in your head. Any rule you add, you know where it goes. Specificity conflicts are rare and easy to fix. Then the project grows. Somewhere between 1,500 and 3,000 lines, the first cracks appear: a new feature requires overriding an existing rule, and the only way to win is a more specific selector. The loser adds a doubled class. The winner responds with !important. Three months later the file is 5,000 lines and nobody touches it without fear.

This is not a talent problem. It is a compounding problem. Every rule added without a rule about where it goes multiplies the ambiguity of every future rule. After a few hundred such additions, the cost of any change is unbounded.

Architecture is the opposite of style

"Make this button blue" is a style decision. "The button belongs in the components layer and uses a token from tokens" is an architectural decision. Both are necessary. Most teams only make the first one, consciously. The second one gets made implicitly, badly, a thousand times a day by whoever is editing the file.

PE7 exists to make the architectural decision once, up front, and then make it impossible to violate. That is the whole point of naming your layers before you write a single rule.

Intent, encoded

When a new engineer opens a PE7 codebase and sees @layer reset, tokens, base, layout, components, animations; on line 1 of the root stylesheet, they already know:

  • Where every kind of rule is supposed to live.
  • What can override what.
  • Which layers they are allowed to add to without reading the whole project.
  • What changes will be reversible and what will not.

That is a one-line specification for the entire codebase. No onboarding doc can match it.

The architectural test

A good architecture answers a single question in under ten seconds: "If I need to add rule X, where does it go?" If the answer requires discussion, the architecture is failing. If the answer requires reading other files, the architecture is failing. If the answer is "depends on what breaks," the architecture does not exist.

The six PE7 layers are specifically designed so that every well-formed CSS rule has exactly one correct home, and moving it anywhere else breaks something visible.

Illustration — intent, on line 1

/* root.css, line 1 — the entire architecture */
@layer reset, tokens, base, layout, components, animations;

/* From this line, a new engineer already knows:     */
/*  - resets are the weakest thing in the cascade     */
/*  - animations can override anything below          */
/*  - tokens never contain selectors, only variables  */
/*  - layout cannot paint colors or set fonts         */
/*  - components are classes, never elements          */

Try it yourself

Mini-exercise

Take any CSS file from a project you currently work on. Without running anything, mentally assign every rule to one of the six PE7 layers. Count how many rules you cannot confidently place — those are the rules where your current architecture is silent. Bring that count to Lesson 3.2.
