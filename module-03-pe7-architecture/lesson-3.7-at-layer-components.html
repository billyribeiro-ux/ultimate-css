Lesson 3.7

@layer components

Named UI pieces. This is where buttons, cards, dialogs, badges, and forms live. Each component has one responsibility, uses semantic tokens, and exposes its own customisation surface through scoped custom properties.

The single responsibility

A component in the components layer is a reusable, named piece of UI with a single semantic purpose. A .btn is an action trigger. A .card is a grouped content container. A .badge is a short status indicator. If a rule targets a named piece of UI, it belongs here. If it targets raw elements or layout primitives, it does not.

Components are always classes. Never elements, never IDs.

Scoped custom properties — the core pattern

Every component exposes its variable surface through custom properties namespaced to the component. Consumers theme the component by setting those properties. The component itself reads from them with sensible defaults:

@layer components {
  .btn {
    --btn-bg:      var(--color-brand);
    --btn-fg:      #fff;
    --btn-padding: var(--space-2) var(--space-4);
    --btn-radius:  var(--radius-md);

    display: inline-flex;
    align-items: center;
    gap: var(--space-2);
    background: var(--btn-bg);
    color:      var(--btn-fg);
    padding:    var(--btn-padding);
    border-radius: var(--btn-radius);
    border: 0;
  }

  .btn.danger {
    --btn-bg: var(--color-danger);
  }

  .btn.ghost {
    --btn-bg: transparent;
    --btn-fg: var(--color-brand);
    box-shadow: inset 0 0 0 1px var(--color-brand);
  }
}

Notice what the .danger and .ghost variants do: they change one custom property each. They do not rewrite the whole rule. They do not fight specificity. They do not need !important. The component owns its customisation surface; variants are configuration, not override.

The single responsibility test, applied

Before shipping a component, answer: "What is this component's one job?" If you cannot say it in a single clause, the component is two components. Split them.

  • .btn → "trigger an action."
  • .card → "group related content visually."
  • .badge → "display a short status label."
  • .dialog → "present modal content."

A .card-with-header-and-footer-and-buttons is not a component. It is a layout of components. The individual pieces each live in the components layer; the composition lives in whichever page or feature uses them.

What components must not contain

  • No element selectors at the top level. .card h2 { ... } is fine inside the card; h2 { ... } standalone is base.
  • No layout primitives. A card does not redefine .stack; it consumes it from layout.
  • No raw colour values. Every colour resolves through tokens.
  • No component reaching into another component by name. .card .btn { ... } is a code smell — it means the component is trying to own something it does not own.
  • No !important. If you need it, the architecture is wrong, not the rule.

Component files

In practice, each component lives in its own file: components/btn.css, components/card.css, components/dialog.css. All of them are imported into the components layer via @import url("./components/btn.css") layer(components);. The file boundary and the layer boundary reinforce each other.

Mini-exercise

Add a new variant .btn.success that uses a green brand colour. You should only need to set one custom property to do it. If you find yourself rewriting the whole rule, you are fighting the component instead of configuring it — back up and try again.
